# ピコ窓 要件定義書 v1.0

- 初版作成：2026-10-11 JST
- 正式版：2026-10-12 UTC
- 対象：PicoMado の初版 LCD・４ボタン端末と、複数端末・E-ink 対応を可能にする共通基盤

第１〜６章の主文にある「〜する」「〜できる」は確定した要件を示す。実験結果と既存機の伝聞は検証範囲を明示し、製品での実証と区別する。実装方法や数値が未確定の項目は第８章に U 番号を維持して記載する。第６章の AC 番号は受入条件であり、初版 LCD １台の受入と、追加端末・結線後の確認を分ける。既存システムの改修や E-ink 製品への移行は本書の承認範囲に含めない。

## 1. 目的と範囲

Pico W、0.96 インチ ST7735S カラー LCD、４タクトスイッチ、Pi5 を母艦とする既存 YouTube エンドレス再生デバイスを土台に、機能を追加・変更できる「ピコ窓（PicoMado）」を構築する。LCD の表示は 160×80 ピクセル（パネルの物理表記は 80×160）。メインシステムとプラグインは同じポート上の API エンドポイントで扱う。プラグインの実行場所やインターフェースの詳細は未決（U-03、U-04）。

一つのサービスで複数端末の独立したセッションを扱える構造とし、LCD ４ボタン端末と電子ペーパー（E-ink）２ボタン端末で対応可能なプラグインを共用できるようにする。端末ごとのディスプレイ種別やボタン数などを Web UI で設定できる構造も要件とする。具体的な方式や対応範囲は設計事項（U-02～U-04）。E-ink 端末の静止画・更新頻度の制約を LCD へ一律に適用しない。共有可能な基盤の設計と、既存 E-ink 製品への実装移行は別の判断とし、後者は今回承認されていない。

稼働確認と初版完成の対象は LCD・４ボタンの PicoMado １台とする。複数端末を扱える基盤要件は維持するが、複数実機で検証済みとは扱わない。E-ink・２ボタン端末は画面部品がまだなく、端末が完成してから実機確認する。将来の利用候補として、既存のボタンなし風刺画端末を初期プラグインのみ表示するダミー端末に使ってもよい。既存端末の書換えを今回許可したものではない（U-15）。

### 気象庁データの採用範囲と検証限界

天気・雨雲とも気象庁の公開データを情報源として採用し、その提供範囲内で表示する。天気の Web 設定地点は、対応する**予報区域**と**気温の代表地点**に結び付ける。東京駅を含む任意の設定地点について、その地点そのもののピンポイント予報と誤認させず、画面で予報区域と気温地点を区別して示す。提供されない気温は `ーー` と表示し、0 と扱わず、実測値と予測値を混ぜて補わない。湿度は取得できる場合のみ表示し、この確認済み予報 JSON にない値を無理に補完しない。

**調査済みの公開例・製品未実装。** [東京都の気象庁予報 JSON](https://www.jma.go.jp/bosai/forecast/data/forecast/130000.json) では、確認時点で週間予報は明日から７日分で、初日の気温欄に空値があった。今日を含む７日分には短期予報と週間予報を対象日付で結合する案を設計候補とする。区域・代表地点への対応、欠損を含む日付結合、全設定地域での取得・表示は未検証（U-10）。

**調査済みの公開例・製品未実装。** 気象庁の[高解像度降水ナウキャストの説明](https://www.jma.go.jp/jma/kishou/know/kurashi/highres_nowcast.html)と公開時刻一覧 [N1](https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N1.json)・[N2](https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N2.json)を Web で読み取り、確認時点では過去３時間・未来１時間の範囲だった。対象時刻のデータがそろう場合に１時間刻みで最大５画面とする案だが、将来もこの範囲が固定される保証はない。毎時取得したセット内の最新**観測**を既定画面とし、対象時刻と観測／予測の区別を表示する。PNG タイル本体の取得・プログラムによる合成プレビューは[雨雲描画実験](../experiments/jma-radar-render/README.md)で行ったが、海岸線の可読性は受入条件を満たしておらず、Pico 実機への描画は未検証（U-10、U-14）。さらに長い予測を別製品と混合する仕様は決めていない。

[天気描画実験](../experiments/jma-weather-render/README.md)では、東京駅向けの７日分をプログラムで PNG に描き、LCD 160×80 と E-ink １bit 250×122 のプレビュー表示方式を確認した。この画面の配置・表現を採用する。両実験の画像生成に LLM は使用しておらず、どちらも実機画面の表示結果ではない。天気の他地域や端末での見え方は未検証（U-10）。

これらは気象庁サイトの公開表示用データであり、[同庁の案内](https://www.jma.go.jp/jma/kishou/info/coment.html)について外部開発向け固定 API や SLA は確認していない。情報源は気象庁とする。取得・結合・合成・端末表示の成立は別途検証する。

## 3. 複数端末・プラグイン・接続

一つの Pi サービスで複数端末に対応できる構造とし、端末 ID ごとの独立した論理セッションを扱う。論理セッションは操作・表示・接続状態を管理する単位であり、常時 TCP 接続を義務づけない。一台の待機や切断が他端末の操作・画面・再生を変えない。共通サービスの具体的な配置・通信 API の詳細・復帰手順は未決（U-02、U-03）。

同じ device_id の端末が再接続したら、新しい接続を有効とし、旧接続を終了する。旧接続から遅れて届く操作・応答・切断 callback で新しいセッションの状態やオンライン表示を変更しない。接続世代番号などの識別方法は設計事項（U-02）。これは同一端末の再接続を扱う規則であり、別々の Pico に同じ device_id を誤設定した衝突とは区別する。新しい認証キーの導入を初版の必須要件としない。

Pico からの通信が届いた時点で device_id を基に端末を自動登録する。初版の LCD・４ボタン端末は初回に４プラグインをすべて利用 ON とし、共通初期順序は YouTube→風刺画→天気→雨雲レーダー、初回表示は YouTube とする。Web UI で端末 ID ごとに利用可能なプラグインを ON/OFF チェックし、その設定を Pi サービスが永続保存する。共通順序を変更した後も各端末では利用 OFF の項目を除いて使い、前回表示したプラグインが無効なら利用可能な先頭を表示する。能力非対応のプラグインは Web UI に理由を表示して利用 ON にできず、初回登録時も ON にしない。すべて無効なら画面中央に「PICO窓」を表示し、少なくとも Web UI から設定できる状態を保つ。通常接続中は本体設定メニューを設けず、プラグイン選択順序の末尾にも追加しない。起動・再接続・接続失敗中の設定入口は第４章のとおり維持する。

Web UI の共通設定にプラグイン一覧を置き、↑↓ボタンで並べ替えて保存する。保存した全端末共通の順序を使い、端末ごとに利用 OFF の項目は選択列から除く。初期順序は上記の４機能順とし、画面の細かな配置だけを設計事項とする（U-04）。

Web UI のホームに各プラグインページへの入口を置き、各プラグインページにホームへ戻るボタンを置く。メインシステムとプラグインは同じポートで提供し、API エンドポイントで機能を制御する。新プロジェクトのポート番号自体は未決（U-08）。

### プラグイン Web 画面の構成

各プラグインの Web 画面では、共通コンテンツエリアとデバイスごとの設定項目を分けて構成する。共通コンテンツエリアの操作がどの端末へ影響するかはプラグインが決め、全プラグインで全端末への反映を強制しない。端末ごとのプラグイン利用可否の ON/OFF は共通基盤が管理する設定であり、プラグイン固有の端末別設定項目とは区別する。天気の地域はプラグイン固有の端末別設定とし、各端末の初期地点を東京都の東京駅にする。Web UI の天気プラグイン設定では気象庁の対応地域・気温代表地点の一覧から端末ごとに選び、ほかの端末の地域は変えない。初版では住所の自由入力や GPS からの自動変換を設けない。変更した地域は端末固有設定として保存し、サービス再起動後も保持する。画面内の具体的な項目・対象端末の指定方法は設計事項（U-04、U-14）。

共通基盤がページの共通枠と対象端末の選択 UI を提供し、プラグインが共通コンテンツエリアと端末別設定エリアの項目・処理を提供する。操作が共有対象へ作用するか対象端末へ作用するかを画面上で示す。端末別項目のないプラグインには無理に項目を作らない。共通エリアの内容や操作の影響範囲はプラグインが決め、基盤は全端末への一律反映を強制しない。画面の具体的な配置と項目の受け渡し方法は設計事項（U-03、U-04）。

プラグインは Web 画面に加え、共通の登録・入力配送・描画送信手段を利用する拡張単位とする。具体的な登録形式とインターフェースは未決（U-03、U-04）。

共通基盤は device_id、接続、端末ごとの選択プラグインと表示能力を管理し、入力イベントを該当プラグインに配送する。プラグインが指定した端末へ描画を送る手段も提供する。表示内容、端末間の共有範囲、再生状態と送信先の選定は各プラグインの責務とする。基盤が「同じプラグインを選んだ全端末へ同じ内容を送る」規則を強制しない（具体的なインターフェースは U-03）。

端末ごとの選択プラグインは Pi の共通基盤で管理する。現在表示すべき内容とプラグイン内の操作状態は、基本的にサーバ側の該当プラグインが保持し、Pico は受け取った内容を表示する。共通基盤は通信、待機、入力モード、接続中画面を引き続き扱う。保存済み設定・取得データと、一時的なサブモード・閲覧位置は区別する。再起動後は前回選択プラグインの通常画面から始め、一時的なサブモードと閲覧位置は復元しない。天気は今日、雨雲は取得セット内の最新観測を通常表示する。保存方式の詳細は設計事項（U-06）。Pico は下／次、上／前などのボタン操作を通知し、基盤が共通の切替処理で選択状態を更新する。プラグインは入力イベントを受け、内容と送信先を決め、基盤の送信手段で端末へ描画を届ける。サーバから自身への HTTP 呼出しは必須ではない。サーバ側で表示対象を更新したことと、端末画面に実際の表示が完了したことは同一視しない。完了通知・確認方法は U-03。

サブ機能ボタンには、項目一覧を表示するメニュー型と、動的なアクションを行う操作モードへ入る型の２通りを共通基盤として用意する。基盤は共通の入力・表示・モード管理を提供し、型の選択、具体的な動作と状態はプラグインが担う。天気と雨雲レーダーは時系列の操作モード型、YouTube と風刺画は当面サブ機能なしで押下しても無反応とする（第４章）。

初期の Pico ファームに、共通のメニュー表示・操作を行う基盤を実装する。この基盤が扱える範囲では、サーバから渡すメニュー項目を後から追加できる構成を目指す。メニューのデータ形式・画面遷移・対応範囲は設計事項（U-03、U-05）。基盤の対応能力を超える表示・入力や新しいハード機能まで、サーバ側だけで追加できるとはしない。項目一覧メニュー型と、天気・雨雲の時系列を含む動的操作モード型の両方を扱う。

`systemd` は Pi サービスの起動・監視を担い、接続中の端末を判定する主体ではない。Pi サービスが端末 ID とセッションを基に接続状態を管理する。heartbeat などの具体的な生存確認方式は設計事項。

オフライン端末も Web UI に状態表示し、設定できる。オフライン中の変更は保存し、再接続時に適用する。不要端末は Web UI から削除でき、Pi サービス側の端末利用設定を除去する。オンライン端末を削除したときは現在のセッションも終了する。Web UI には再接続すると新規端末として一覧に再登場する旨を示す。削除済みの device_id が再び通信してきたら、旧端末固有設定を復活させず、対応可能な初期プラグインを ON にした新規端末として自動登録する（初版 LCD 端末では４機能 ON）。順序はその時点で保存されている全端末共通順序を適用し、未変更なら初期順序の先頭である YouTube を表示する。Web で手動登録する操作は設けない。端末側の Wi-Fi 資格情報やファームを消す工場初期化は行わない。

情報取得・更新、表示内容、プラグイン内の操作状態と共有範囲は各プラグインが担当する。端末ごとの選択プラグイン、省電力、接続状態は基盤が扱い、非選択機能や別端末からの意図しない画面上書き・停止・操作の混入を防ぐ。表示能力差と物理ボタンの論理入力への変換方法は設計時に選ぶ（U-03、U-04）。

画面サイズ・色深度・更新頻度などの端末能力を管理し、プラグインの対応可否を判定する。必要能力の宣言形式は設計時に定める（U-03）。 端末能力上対応できないプラグインは Web UI に非対応の理由を示し、利用 ON にできない。E-ink 端末でも YouTube は制限付きの対応機能として選択できるようにする。滑らかさや LCD と同等の品質は保証せず、飛び飛びの表示を許容する。端末能力に応じたフレーム間引きなどの転送・描画方法は設計事項（U-03、U-14）。ほかのプラグインを全端末で同じ形で表示できるとは限らない。既存 E-ink 製品の改修・移行は今回承認されていない。

### 複数端末での YouTube 共有

初期 YouTube プラグインは、視聴端末間で動画と再生位置を共有する。各端末のプラグイン選択と待機・接続状態は独立する。端末 A が天気へ切り替えても視聴中の端末 B は止まらず、A が YouTube に再参加すると共有中の現在位置から表示する。動画の変更は、その時点で YouTube を視聴している全端末へ反映する。フレーム単位の厳密な同期は要求せず、遅い端末がほかの端末の配信を止めない。共有コンテンツ・再生状態と端末固有の状態を区別し、YouTube プラグインが共有範囲・再生状態・送信先を管理する。視聴端末数に応じる PUSH 接続数・帯域、共有位置の更新基準、遅い端末の送信処理、表示能力が異なる端末間での扱いは設計・測定事項（U-14、U-15）。

基盤は、将来プラグインが端末別の再生状態を持ち、対応済みの描画・入力能力の範囲で異なる動画を表示できる構造とする。他プラグインにも共有を強制しない。新しいコーデックやハード機能までファーム変更なしで対応できるとは約束しない（U-03、U-14）。

### 設計・試験で具体化する案（実装方式は未決）

接続世代と表示内容の切替世代を別に識別し、遅延フレームや ACK が現在の表示を上書きしない契約を検討する。ACK には対象の表示／フレームを識別できる情報が必要になる。接続世代番号や表示世代番号そのものの採用は未決で、同一端末再接続時に新接続を優先する既決規則を満たす方式を選ぶ（U-02、U-03）。

TCP 上のメッセージは長さと種別を判別できるフレーミング、分割受信、異常な長さ・破損・タイムアウト時の処置を設計する。受信したことと LCD／E-ink への描画が完了したことは区別し、それぞれの ACK／通知が何を保証するかを定める。端末ごとに有界の送信待ちを設け、送信前に古くなった動画フレームを破棄する案を評価する。遅い端末が別端末の送信を止めず、共有中の動画位置は YouTube プラグインが管理する既決の責務分担を守る（U-02、U-03、U-14、U-15）。

定期取得と１時間経過による即時取得が重なる場合は重複実行を抑える案を検討する。取得状態を `EMPTY`／`FETCHING`／`READY`／`STALE`／`ERROR` などで区別するのは設計候補であり、遷移と再試行は未決。最後の正常取得時刻を鮮度判断に使い、再試行後も失敗したときはプラグインのエラー描画にする既決規則を維持する。同じ地域・同じ対象日時の天気データは端末間で共通取得を再利用できるか検討するが、端末別の地域設定は保つ（U-10、U-14）。

設定の正本を、端末側 Wi-Fi・ハード／端末 ID、基盤が扱う共通順序・端末別利用可否・選択プラグイン、プラグインが扱う地域・コンテンツ、一時的な入力モードに分けて明文化する。一時モードの端末・サーバ間の同期と、保存すべき設定の原子的な更新を設計する。接続設定の移行時には旧接続試行を無効化し、遅れて届く完了通知で新しい選択を戻さない。ビルド時には同じ device_id の重複を検出する案を検討する。別端末の ID 誤設定・なりすましへの耐性は同一端末再接続とは別課題であり、新しい認証キーを初版必須にはしない（U-02、U-05、U-06、U-17、U-18）。

端末別の状態・最終通信時刻・エラー種別をログと Web UI でどのように示すかを設計し、全国地図が小画面で判読できるか実験する。各要件と対応する試験の期待結果・合否を紐付ける。応答時間、接続復帰時間、動画 fps・遅延、長期安定、消費電力、他プラグインへの阻害を測定項目とするが、合格閾値や測定期間はまだ定めない（U-03、U-04、U-10、U-14、U-15）。

### 共通ソース、設定とビルド

共通ソースは端末ごとにコピーせず共有する。共通設定、ハード構成プリセット、端末別上書きを分け、端末 ID 単位でビルド出力フォルダと UF2 を分離する。端末別 Config にボタン定義を持ち、日常の機能選択や利用可能プラグインなどは端末が対応できる範囲で Web UI から設定する。ハード対応はファームウェアが提供する範囲に限られ、Web 設定だけでドライバや物理配線は変更できない。設定形式・CLI・ディレクトリ構成とビルド手順は未決（U-04、U-17）。端末 ID は IP と分離し、IP 固定値のファーム焼込みを必須としない。DHCP 予約は選択肢の一つ（U-08、U-17）。

### Wi-Fi プロファイルと接続経路

SSID とパスワードのペアを複数登録し、端末設定のネットワーク項目で家／外出先テザリングを選べるようにする。秘密値は Git 管理外に置き、`config.sample` などに実値を書かない。自宅は Pi5 の自宅 LAN アドレスへの direct TCP、外出先は Pico からスマートフォンの TailSocks SOCKS5 に接続して Pi5 の Tailnet アドレスへ進むプロファイル方針が了承された。両プロファイルの宛先は同じ Pi サービスでも IP と経路が異なる。Wi-Fi の選択・再試行とメニュー操作は第４章、設定の保存方式や失敗後の扱いは U-18。

**実測済みの範囲。** [接続技術ガイド](home-away-connectivity-technical-guide.md) と [2026-10-11 の実験記録](../experiments/tether-tailnet/results-2026-10-11-tailsocks.md) によると、非 root の Android 16 上の TailSocks v4.9.1 で、Pico → スマートフォンのテザリング側 `10.101.65.232:48115`（SOCKS5 認証）→ Pi5 Tailnet `100.64.0.9` の接続が成功した。Pi5 は TailSocks ノード `100.64.0.18` からの着信として観測した。同じ Pico 起点の持続 TCP 上で Pi5 の PUSH と Pico の ACK も成功した。これらの値は試験時のアドレス・ポートであり、特にテザリング側 IP は固定保証がない。SOCKS5 が指定された TCP を中継した結果で、スマートフォンのホットスポット全体を透過的に VPN 化したものではない。

**未検証。** 自宅 direct TCP の新方式での実測、既存アプリへの取り込み、長時間接続、動画帯域・遅延、切断・切替後の復帰、複数端末での動作は確認していない。プロファイル内でサーバ宛先と SOCKS5 接続先をどう保存・更新するかも設計事項（U-15、U-18）。既存の YouTube 本番サービス、Tailscale、ルータ設定はこの文書改訂で変更しない。

## 4. 起動・接続・ボタン操作

物理的な電源投入時には、前回選択したネットワークへの接続を試みる。接続成功は Wi-Fi 接続だけではなく、Pi アプリケーションのセッション確立までを指す。成功後は前回選択したプラグインの通常画面を表示する（無効時は第３章の規則を適用）。再起動前に時系列などのサブモードを開いていても、その閲覧位置は戻さず、天気は今日、雨雲は取得セット内の最新観測を表示する。失敗した場合は選択中のネットワークで再試行し、回数に上限を設けず電源 OFF まで繰り返す。プラグイン稼働後に Wi-Fi が失われた場合も画面を「Wifi接続中」に切り替え、起動時と同じ選択中ネットワークの再接続を繰り返す。Wi-Fi がつながっていても Pi サービスに到達できない場合やアプリケーションのセッションが切れた場合は「サーバ接続中」と表示し、同じネットワーク／接続経路でセッション確立まで再接続を繰り返す。試行タイムアウトと再試行間隔は Config で設定可能にする。具体的な既定値は未決（U-18）。別プロファイルへの自動切替は未合意。ここでいうボタンによる「電源 OFF」は物理的な給電遮断ではなく、省電力待機を指す。待機中は Wi-Fi を停止してよい。コンセントを抜く物理断は別の状態である。

単なる一時的な通信断でも選択中の同一プロファイルで再接続し、Pi アプリケーションのセッション成立後は前回選択プラグインの通常画面に戻る。通信断前の一時的なサブモードや閲覧位置は復元しない（無効なプラグインの場合は第３章の規則を適用）。セッション復帰の具体的な手順は設計事項（U-02）。

### 主な状態と遷移

| 現在の状態 | 契機 | 次の状態・表示 | 確認条件 |
| --- | --- | --- | --- |
| 物理起動・待機 | 起動・復帰 | 前回選択ネットワークの接続試行。「Wifi接続中」 | 前回ネットワークを使い、一時的なサブモードは復元しない。 |
| Wi-Fi 接続中 | Wi-Fi 成立 | Pi アプリセッション確立を試行。「サーバ接続中」 | Wi-Fi 成立だけで通常画面に進まない。 |
| サーバ接続中 | アプリセッション成立 | 前回選択プラグインの通常画面 | 無効なら第３章の選択規則を適用する。 |
| 通常画面 | Wi-Fi 喪失／アプリセッション断 | それぞれ「Wifi接続中」／「サーバ接続中」 | 同じプロファイルで再試行し、復帰後は通常画面へ戻る。 |
| 接続試行中 | サブ機能入力 | 試行をキャンセルして本体設定メニュー | メニュー中は再試行を止め、確定／キャンセルは次段落の規則に従う。 |
| 通常画面 | サブ機能入力（対応プラグイン） | 時系列操作モード | 閲覧中の取得セットを維持し、キャンセルで最新セットの既定画面へ戻る。 |
| 通常画面・操作モード | 電源／待機入力 | 省電力待機 | LCD は黒表示、E-ink は直前画像を保持し、更新しない。 |

状態の実装表現、試行タイムアウト、接続世代と表示世代の扱いは U-02・U-03・U-18 で設計する。

起動時、プラグイン稼働後の Wi-Fi 喪失時、Wi-Fi 接続中の Pi サービス不達時のいずれも、接続失敗中や接続作業中にはサブ機能入力（４ボタンでは左上、２ボタンでは上長押し）から本体設定メニューを開ける。この入力は接続処理中にはプラグインへ渡さない。接続作業中に押した場合は進行中の接続をいったんキャンセルする。接続設定メニュー中は再試行を停止する。ネットワーク設定項目で家／外出先テザリングを選択でき、決定すると選択を保存して接続する。キャンセルすると変更を破棄し、元のネットワークで接続を再開する。設定メニューのその他の項目や画面遷移は未決（U-05）。

待機中の E-ink は直前の画像を保持し、画面をクリアしない。通知などを受けても待機中に画面を更新しない。LCD は黒画面を表示し、BLK を OFF にする。現状の PicoMado は BLK が未結線のため、ソフトウェア上の黒画面は表示できてもバックライトの物理的な消灯はできない。結線後に BLK の実機極性を確認して OFF 制御を完成させる（U-07）。待機からの復帰時は、物理起動時と同様に前回選択したネットワークへ接続し、接続中画面を表示し、Pi アプリケーションのセッション成立後に前回選択したプラグインの通常画面を表示する（無効時は第３章の規則を適用）。待機前の一時的なサブモードや閲覧位置は復元しない。

選択したネットワークはコンセントを抜いた後も記憶する。技術的に難しい場合に限り、起動時の家プロファイルを既定にしてよい。単純で変更頻度の低い設定を不揮発に保存することは可能だが、保存媒体・書込みタイミング、初回起動やデータ破損時の初期値は設計事項（U-18）。

ボタンの論理役割は端末別 Config で定義する。PicoMado の４ボタンは次の配置とする。GPIO と物理ピン番号は区別する。

| 位置 | GPIO／物理ピン | 通常時の役割 |
| --- | --- | --- |
| 左上 | GP12／16 | サブメニュー |
| 左下 | GP14／19 | 電源兼キャンセル |
| 右上 | GP13／17 | 上選択／前のプラグイン |
| 右下 | GP15／20 | 下選択／次のプラグイン |

E-ink 側の GPIO は未定で、既存 E-ink 製品の改修は別途判断する。

| 位置 | GPIO | 短押し | 長押し |
| --- | --- | --- | --- |
| 上 | 未定 A | 上選択／前のプラグイン | サブ機能呼出し／項目一覧メニュー内の決定 |
| 下 | 未定 B | 下選択／次のプラグイン | 電源・操作モード／メニュー内のキャンセル。待機からの復帰も長押し |

通常時の上下ボタンは、各端末で利用 ON のプラグインを全端末共通の順序で前／次に切り替える。YouTube と風刺画は当面サブ機能なしとし、サブ機能ボタンを押しても無反応でよい。天気と雨雲レーダーはサブ機能ボタンで時系列操作モードに入り、上下で時点を変える。電源ボタンをキャンセルとして押すと、デフォルト表示へ戻ってモードを終了する。時系列操作モードは項目一覧から決定するメニューとは区別する。基盤が両型の共通入力・表示・モードを扱い、型の選択と表示時点・内容・取得更新はプラグインが決める。通常接続中に本体設定メニューへの入口は設けない。２ボタン端末では短押し上下で選択・時点移動、上長押しでサブ機能を呼び、下長押しで時系列操作モードをキャンセルする。サブ機能のない YouTube・風刺画では上長押しは無反応とする。４ボタン側の電源ボタンで待機から復帰する従来合意を維持し、押下時間は未決。

デフォルト表示は今日。今日を含む７日分を保持し、表示対象日を分かるようにする。下ボタンは翌日、上ボタンは前日方向へ移動し、今日より前と７日目より後には進まず、その場で停止する。末尾から今日へ循環しない。各日には天気マークと最低・最高気温を表示し、湿度も取得可能なら表示する。欠損する最低・最高気温は `ーー` とし、0 や異なる種別の気温で補わない。表示する予報区域と気温代表地点を区別する。情報源は気象庁に決定した。今日を含む７日分を短期・週間予報から対象日付で構成できるか、予報区域と代表地点の対応を含めて検証する（U-10）。

デフォルトは取得セット内の最新観測時刻の雨雲表示とし、対象時刻および観測／予測の区別を画面に示す。下ボタンで１時間先、上ボタンで１時間前へ進む操作を基本とし、取得済みデータの端ではその場で停止して循環しない。日本列島の地図上に、実際に取得できた時刻の雨雲を描く。最新観測より先へ進むには予測データが必要で、予測がなければ初期位置からの下押下では進まない。取得元は気象庁の高解像度降水ナウキャストとし、確認時点の時刻一覧は過去３時間・未来１時間の範囲だった。対象時刻がそろう場合の１時間刻み最大５画面を設計候補とし、範囲を固定値として保証しない。実際の時刻一覧とタイルの取得・合成を実験プログラムで確認したが、端末描画は未検証とし、存在しない中間時刻の画像は作らない（U-10、U-14）。 日本列島の海岸線は、最終表示解像度の LCD カラー画像と E-ink 向け１bit 変換後の両方で明瞭に判別できなければならない。E-ink 向け１bit 表示では降水強度の細かな表現より、降水域が日本列島のどこにどれほど広がるかを優先する。降水域を一律の黒ベタに簡略化することも許容するが、海岸線の明瞭性は必須とする。黒ベタ・白縁取り・網点はいずれも描画候補で、具体的な方式は未決。ここで示すのは雲全体ではなく降水域である。

天気・雨雲の時系列を閲覧中に毎時更新で新しい取得セットが届いても、その閲覧中は開始時の取得セットを保持し、表示対象日時を勝手に動かさない。キャンセルして通常画面へ戻った時点で最新の取得セットへ切り替え、天気は今日、雨雲はそのセットの最新観測を表示する。取得失敗時のエラー描画という既決規則は維持する。

項目一覧型の本体設定メニューや将来のプラグインメニュー内では、サブ機能入力を決定、電源・キャンセル入力をキャンセルとして統一する。４ボタンの PicoMado では左上 GP12 が決定、左下 GP14 がキャンセル。２ボタンでは短押し上下で項目を選び、上長押しで決定、下長押しでキャンセルする。右上 GP13 と右下 GP15 は上／下の選択、または選択中プラグイン内の操作に使える。項目一覧型メニューにこの共通役割を適用する。天気・雨雲の時系列操作モードでは、上記の時点移動とデフォルト表示へのキャンセルを適用する。項目一覧型メニューでの決定後の画面遷移と、将来のプラグインメニューでキャンセルした際の変更保存／破棄は未決（U-05）。接続設定でのキャンセルは上記のとおり変更を破棄する。

初版の通常接続中は、本体設定メニューを開く入口を設けず、プラグイン選択の末尾にも置かない。各プラグインのサブ機能に本体設定を追加しない。接続失敗中・接続作業中の設定入口は上記の決定どおり維持する。将来必要になった場合の拡張は初版の必須要件としない。

単押しにはチャタリング対策を行う。長押しは 1.5～2 秒程度を想定し、時間を Config で設定可能にする。具体的な既定値やチャタリング時間は未決（U-05）。

短押し上／下は選択、上長押しは通常時のサブ機能呼出しと項目一覧メニュー内の決定、下長押しは電源・操作モード／メニュー内のキャンセルと待機からの復帰に用いる。接続処理中の上長押しは本体設定呼出しを優先する。メニューを開いた長押しが決定として連続発火しないようにする入力判定と、長押し時に短押しを誤発火させない判定は設計事項（U-05）。

| ボタン右下（下／次） | GP15 | 20 |
| ボタン共通 GND | — | 18 |
| LCD BLK（合意済みの割当先） | GP22 | 29 |

既存ボタンは内部プルアップを用い、押下時 LOW。 BLK はハードウェア PWM 対応の GP22（物理29番）へ割り当てる。結線後にソフトウェア側も対応する。待機時は LCD を黒表示にして BLK を OFF にする。ただし現状 BLK は未結線で、黒表示はできてもバックライトの物理的な消灯はできない。比較回路では LOW 消灯／HIGH 点灯だが、実物の回路・極性は未確定（U-07）。極性の設定化と復帰時の元の明るさ保持は設計時の選択肢とする。

元プロジェクトは `/home/tane/dev/PicoW/PicoW_Youtube_Player`。会話上の既存構成では Pi5 が `192.168.0.120`、Pico が `192.168.0.173`、Web が 16152、配信 TCP が 16151 を使用。新機の IP・ポート・運用パス・既存機との併用方法は未決（U-08）。

既存表示では位置調整値 24、RGB 色補正、ガンマ調整、筐体に合わせた 180 度回転を実機承認済みと聞いている。表示を損なわないための継承候補だが、初期化レジスタを含む実際の仕様は元ソース確認後に判断する。

既存の動画方式は、Pi5 が yt-dlp/ffmpeg で取得・変換・キャッシュし、RGB565 フレームを TCP で Pico に配信するもの。Web で URL、切り出し範囲（既定は全体）、履歴・タイトル・作者・サムネイル・容量表示・手動削除を扱い、6/12/18/24/30 fps を選択できると聞いている。既存機能を基本的に移植する方針だが、項目の実態と設定値は元ソース確認が必要で、新環境で 30 fps の達成を保証するものではない。Wi-Fi 性能の変動と、長大キャッシュの走査／共有ロック問題も既存機で経験している。

## 6. 設定・異常系と受入条件

情報取得を行うプラグインでは、取得失敗時にプラグイン設定で変更できる再試行回数に従って再試行する。それでも失敗したら、そのプラグインが用意するエラー描画を表示する。古いキャッシュを常にそのまま表示する方針は採用していない。再試行回数の既定値・間隔・タイムアウト、エラー描画の細部は設計事項（U-14）。以下を受入条件とする。初版の実機確認は LCD・４ボタン１台に限り、E-ink・複数実機・BLK 結線後の確認は各対象が用意された段階で実施する。既存 E-ink 製品の改修は今回の対象に含めない。

1. **AC-01** PicoMado の表示・操作：既存の向き・位置・色、４ボタンの配置と通常／サブ機能／待機の操作、サブメニュー内の GP12 決定・GP14 キャンセル、初期ファームに共通メニュー表示・操作基盤があることを確認する。単押しのチャタリング対策と Config による長押し時間設定も確認する。２ボタン端末の完成後、短押し上下による選択、上長押しによるサブ呼出し・メニュー決定、下長押しによる電源・メニュー取消・待機復帰、接続処理中の本体設定呼出しとメニュー開始押下の分離を別途確認する。BLK 未結線の間は GPIO による消灯を合否対象にしない。
2. **AC-02** BLK 結線後：実物の極性を確認し、消灯・点灯と復帰を確認する。調光・極性設定・明るさ保持を採用した場合はその動作も確認する。
3. **AC-03** 起動・接続：前回選択したプロファイルへの試行、Pi アプリセッション成立後の表示、接続失敗・接続後切断時の同一プロファイルでの無制限再試行を確認する。プラグイン稼働後に Wi-Fi を失ったら「Wifi接続中」、Wi-Fi が生きたまま Pi サービスへ到達できない場合やセッション断では「サーバ接続中」を表示することを確認する。どちらも起動時と同じ再接続、本体設定入口、接続試行のキャンセルを確認する。通常接続中には本体設定入口を設けず、プラグイン選択末尾にも追加しないことを確認する。試行タイムアウト・間隔が Config で変更でき、電源 OFF 中は再試行しないことを確認する。接続設定メニュー中は再試行を停止し、確定で保存・接続、キャンセルで変更破棄・元のプロファイルへ再接続する。サーバ再起動後は前回選択プラグインの通常画面へ戻り、時系列の一時的な閲覧位置を復元しないことを確認する。一時的な Wi-Fi／Pi セッション断からの復帰も前回プラグインの通常画面となり、サブモード・閲覧位置を復元しないことを確認する。待機からの復帰でも前回ネットワークへの接続、接続中画面、Pi アプリセッション成立を経て前回プラグインの通常画面を表示し、待機前のサブモード・閲覧位置を復元しないことを確認する。保存方式の選定に応じ、物理電源断後の選択保持または許容された家既定を確認する。
4. **AC-04** 初期機能：既存 YouTube・風刺画の基本機能をプラグインとして移植し、天気と雨雲レーダーを別プラグインで選択できることを LCD・４ボタン１台で確認する。天気・雨雲ではサブ機能ボタンで時系列操作モードに入り、上下で時点を変え、キャンセルでデフォルト表示に戻って終了する。天気は端末ごとに東京都の東京駅を初期地点とし、Web UI の気象庁対応地域・気温代表地点の一覧から各端末の地域を変更でき、初版では住所自由入力と GPS 自動変換がないことを確認する。変更した地域がサービス再起動後も保持されることを確認する。複数端末がそろった後は、一方の地域変更が他方に影響しないことを確認する。天気は今日を含む７日分を対象とし、表示対象日、各日の天気マーク・最低最高気温と取得可能なら湿度を確認する。今日での上押下と７日目での下押下はその場で停止し、循環しないことを確認する。地域変更や日付切替の後、対象地域・対象日付に対応するデータを表示し、旧設定で進行中だった取得結果が新設定の表示を上書きしないことを確認する。気象庁の短期・週間予報の対象日付結合、予報区域・気温代表地点の表示、欠損気温の `ーー` 表示を確認する。採用した天気 PNG プレビューの配置・表現を基準に LCD 実機表示を確認し、全設定地域での取得・表示の成立を検証する。E-ink 実機表示は端末完成後に確認する。天気・雨雲の時系列閲覧中に毎時更新が入っても閲覧中の取得セットと表示日時が維持され、キャンセル後の通常画面で最新セットに切り替わり、天気は今日、雨雲は最新観測になることを確認する。雨雲は日本列島の地図で取得セット内の最新観測時刻を初期表示し、対象時刻と観測／予測の区別を示す。上下で１時間ずつ前後し、取得済みデータの端で止まって循環せず、存在しない中間時刻の画像を作らないことを確認する。確認時点の公開時刻一覧は過去３時間・未来１時間の範囲だが、その継続や１時間刻みの最大５画面を保証しない。タイル取得・PNG 合成は実験済みとして区別し、実機への転送・描画を別途確認する。LCD の最終解像度と E-ink 向け１bit 変換後のプレビューで日本列島の海岸線が降水域と区別して明瞭に判別でき、実機完成後も同じ条件を満たすことを確認する。E-ink では降水強度の細部より降水域の位置・広がりを把握できることを確認し、黒ベタ表現も合格候補に含める。YouTube・風刺画のサブ機能ボタンは無反応でよい。ライブカメラは次期対象。

## 7. 優先度の低い Want：Bluetooth 音楽再生

**ユーザーの Want。** 所有する Echo Show 5 と第２世代 Echo を、Pico W と Bluetooth 接続するスピーカーとして使い、Web UI で接続先を指定したい。Web UI が機器選択・接続を制御し、Pico が音声を送信する構成を検討する。BTstack 公式の [A2DP Source デモ](https://github.com/bluekitchen/btstack/blob/master/example/a2dp_source_demo.c) と Amazon による [Echo／Echo Show の Bluetooth スピーカー利用説明](https://www.aboutamazon.com/news/devices/connect-alexa-bluetooth) は、この構成を検討する根拠となる。ただし、今回の Pico W と所有する Echo の実機接続、連続再生、Wi-Fi 動画との併用は未検証で、対応や安定動作を保証しない（U-16）。
