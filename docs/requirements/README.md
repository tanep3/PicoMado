# ピコ窓 要件定義書 v1.1

- 初版作成：2026-10-11 JST
- 正式版：2026-10-12 UTC
- 対象：PicoMado の初版 LCD・４ボタン端末と、複数端末・E-ink 対応を可能にする共通基盤

各要件文書の主文にある「〜する」「〜できる」は確定した要件を示す。実験結果と既存機の伝聞は検証範囲を明示し、製品での実証と区別する。実装方法や数値が未確定の項目は「未確定事項と設計時の選択」に U 番号を維持して記載する。本書の AC 番号は受入条件であり、初版 LCD １台の受入と、追加端末・結線後の確認を分ける。既存システムの改修や E-ink 製品への移行は本書の承認範囲に含めない。

## 目的と初版の範囲

Pico W、0.96 インチ ST7735S カラー LCD、４タクトスイッチ、Pi5 を母艦とする既存 YouTube エンドレス再生デバイスを土台に、機能を追加・変更できる「ピコ窓（PicoMado）」を構築する。LCD の表示は 160×80 ピクセル（パネルの物理表記は 80×160）。

稼働確認と初版完成の対象は LCD・４ボタンの PicoMado １台とする。複数端末を扱える基盤要件は維持するが、複数実機で検証済みとは扱わない。E-ink・２ボタン端末は画面部品がまだなく、端末が完成してから実機確認する。将来の利用候補として、既存のボタンなし風刺画端末を初期プラグインのみ表示するダミー端末に使ってもよい。既存端末の書換えを今回許可したものではない（U-15）。

初期バージョンは YouTube、風刺画、天気予報、雨雲レーダーの４つを別プラグインとして提供し、共通順序から独立に選択できる。YouTube と風刺画の再作成方針は次節に示す。既存本番の変更・移行は今回許可されていない。ライブカメラは次期バージョンへ延期する。既存実装の具体的な機能と新環境での表示性能はソース・実機で確認する（U-01、U-09、U-10）。

## 実装方針と文書構成

Pi5 のサーバと初期プラグインは Rust、Pico 側のファームウェアは C/C++ を想定する。既存 YouTube・風刺画の Python 構造をそのまま移すことを前提とせず、機能・例外・運用上の工夫を調査して継承し、Rust プラグインとして再作成する。既存の本番サービスはこの作業で変更しない。

Web UI と API、Pico の端末通信は自宅 LAN と Tailnet 内でのみ利用し、インターネットへ直接公開しない。PicoMado 独自の API キーや Web ログイン登録は設けない。初期ポートは TCP 16153 とし、確認済み値の変更場所は[初期値・検証範囲](../initial-values-proposal.md)に従う。端末別接続・生存確認・２ボタン長押しは端末設定、気象取得は各プラグイン共通設定が所有する。YouTube FPS は各変換要求で必須指定する。外出先の Pico が使う TailSocks の SOCKS5 認証は既定の接続経路として維持する。通信内容の長さ・種類や Web 入力の検証、秘密値を Git やログへ出さない扱いは維持する。これは利用範囲の要件であり、稼働中の OS・ルータ・Tailscale 設定の変更を指示しない。

契約・構造・状態遷移の設計思想は、ユーザー指定の [soukoban](https://github.com/tanep3/soukoban) を参照・採用する。具体的な trait、API、ライブラリ、通信形式はここで確定せず、U-02・U-03 などの設計事項とする。

## プラグイン共通運用要件

風刺画・天気・雨雲レーダーは各プラグインがサーバ側で１時間ごとに取得・更新し、選択時には準備済みの表示内容を速やかに送る。取得・表示内容はプラグインの責務であり、画面転送や物理的な更新がゼロ秒になる保証ではない。時系列の表示素材を事前準備する方式は設計時に選ぶ（U-10、U-14）。取得失敗時の扱いは本書の「受入条件」。保存済みの取得データを利用し、その最後の正常取得時刻から１時間以上経過していれば直ちに再取得する。失敗した試行だけで鮮度判定の起点を更新しない。天気の地域と対象日、雨雲の対象日時を取得データと結び付け、時系列の選択を単なる配列添字だけで管理しない。天気の地域変更や日付切替に伴って必要なデータを無効化・再取得し、旧設定で進行中だった取得結果で新設定のデータや表示を上書きしない。毎時更新だけでは閲覧中の取得セットを置き換えない（[共通カーネル](kernel.md)）。１時間ごとの事前更新と併用し、再取得に失敗した場合は本書の「受入条件」の再試行とエラー描画に従う。表示対象日時が保持範囲外になった場合の具体的な処置、再取得中に何を表示するかと保存形式は設計事項（U-10、U-14）。

情報取得を行うプラグインでは、取得失敗時にプラグイン設定で変更できる再試行回数に従って再試行する。それでも失敗したら、そのプラグインが用意するエラー描画を表示する。古いキャッシュを常にそのまま表示する方針は採用していない。天気・雨雲の外部 HTTP 取得は各回 20 秒、追加再試行２回を初期値とし、両値を各プラグインの Web UI で個別に変更・保存する。再試行間隔とエラー描画の細部は設計事項（U-14）。

天気・雨雲の時系列を閲覧中に毎時更新で新しい取得セットが届いても、その閲覧中は開始時の取得セットを保持し、表示対象日時を勝手に動かさない。キャンセルして通常画面へ戻った時点で最新の取得セットへ切り替え、天気は今日、雨雲はそのセットの最新観測を表示する。取得失敗時のエラー描画という要件は維持する。

### 公開気象データに関する検証限界

これらは気象庁サイトの公開表示用データであり、[同庁の案内](https://www.jma.go.jp/jma/kishou/info/coment.html)について外部開発向け固定 API や SLA は確認していない。情報源は気象庁とする。取得・結合・合成・端末表示の成立は別途検証する。

定期取得と１時間経過による即時取得が重なる場合は重複実行を抑える案を検討する。取得状態を `EMPTY`／`FETCHING`／`READY`／`STALE`／`ERROR` などで区別するのは設計候補であり、遷移と再試行は未決。最後の正常取得時刻を鮮度判断に使い、再試行後も失敗したときはプラグインのエラー描画にする既決規則を維持する。同じ地域・同じ対象日時の天気データは端末間で共通取得を再利用できるか検討するが、端末別の地域設定は保つ（U-10、U-14）。

## 受入条件

以下を受入条件とする。初版の実機確認は LCD・４ボタン１台に限り、E-ink・複数実機・BLK 結線後の確認は各対象が用意された段階で実施する。

1. **AC-01** <a id="ac-01"></a> PicoMado の表示・操作：既存の向き・位置・色、４ボタンの配置と通常／サブ機能／待機の操作、サブメニュー内の GP12 決定・GP14 キャンセル、初期ファームに共通メニュー表示・操作基盤があることを確認する。単押しのチャタリング対策と２ボタン端末での Web 設定による長押し時間（初期 1.8 秒）の保存・同期も確認する。２ボタン端末の完成後、短押し上下による選択、上長押しによるサブ呼出し・メニュー決定、下長押しによる電源・メニュー取消・待機復帰、接続処理中の本体設定呼出しとメニュー開始押下の分離を別途確認する。BLK 未結線の間は GPIO による消灯を合否対象にしない。
2. **AC-02** <a id="ac-02"></a> BLK 結線後：実物の極性を確認し、消灯・点灯と復帰を確認する。調光・極性設定・明るさ保持を採用した場合はその動作も確認する。
3. **AC-03** <a id="ac-03"></a> 起動・接続：前回選択したプロファイルへの試行、Pi アプリセッション成立後の表示、接続失敗・接続後切断時の同一プロファイルでの無制限再試行を確認する。プラグイン稼働後に Wi-Fi を失ったら「Wifi接続中」、Wi-Fi が生きたまま Pi サービスへ到達できない場合やセッション断では「サーバ接続中」を表示することを確認する。どちらも起動時と同じ再接続、本体設定入口、接続試行のキャンセルを確認する。通常接続中には本体設定入口を設けず、プラグイン選択末尾にも追加しないことを確認する。Wi-Fi 試行 15 秒、Pi アプリセッション試行 10 秒、再試行間隔 5～30 秒の初期値を Web で端末別に変更・保存でき、電源 OFF 中は再試行しないことを確認する。接続設定メニュー中は再試行を停止し、確定で保存・接続、キャンセルで変更破棄・元のプロファイルへ再接続する。サーバ再起動後は前回選択プラグインの通常画面へ戻り、時系列の一時的な閲覧位置を復元しないことを確認する。一時的な Wi-Fi／Pi セッション断からの復帰も前回プラグインの通常画面となり、サブモード・閲覧位置を復元しないことを確認する。待機からの復帰でも前回ネットワークへの接続、接続中画面、Pi アプリセッション成立を経て前回プラグインの通常画面を表示し、待機前のサブモード・閲覧位置を復元しないことを確認する。保存方式の選定に応じ、物理電源断後の選択保持または許容された家既定を確認する。
4. **AC-04** <a id="ac-04"></a> 初期機能：既存 YouTube・風刺画の機能・例外・運用上の工夫を抽出し、Rust プラグインとして再作成し、天気と雨雲レーダーを別プラグインで選択できることを LCD・４ボタン１台で確認する。天気・雨雲ではサブ機能ボタンで時系列操作モードに入り、上下で時点を変え、キャンセルでデフォルト表示に戻って終了する。天気は端末ごとに東京都の東京駅を初期地点とし、Web UI の気象庁対応地域・気温代表地点の一覧から各端末の地域を変更でき、初版では住所自由入力と GPS 自動変換がないことを確認する。変更した地域がサービス再起動後も保持されることを確認する。複数端末がそろった後は、一方の地域変更が他方に影響しないことを確認する。天気は今日を含む７日分を対象とし、表示対象日、各日の天気マーク・最低最高気温と取得可能なら湿度を確認する。今日での上押下と７日目での下押下はその場で停止し、循環しないことを確認する。地域変更や日付切替の後、対象地域・対象日付に対応するデータを表示し、旧設定で進行中だった取得結果が新設定の表示を上書きしないことを確認する。気象庁の短期・週間予報の対象日付結合、予報区域・気温代表地点の表示、欠損気温の `ーー` 表示を確認する。採用した天気 PNG プレビューの配置・表現を基準に LCD 実機表示を確認し、全設定地域での取得・表示の成立を検証する。E-ink 実機表示は端末完成後に確認する。天気・雨雲の時系列閲覧中に毎時更新が入っても閲覧中の取得セットと表示日時が維持され、キャンセル後の通常画面で最新セットに切り替わり、天気は今日、雨雲は最新観測になることを確認する。雨雲は日本列島の地図で取得セット内の最新観測時刻を初期表示し、対象時刻と観測／予測の区別を示す。上下で１時間ずつ前後し、取得済みデータの端で止まって循環せず、存在しない中間時刻の画像を作らないことを確認する。確認時点の公開時刻一覧は過去３時間・未来１時間の範囲だが、その継続や１時間刻みの最大５画面を保証しない。タイル取得・PNG 合成は実験済みとして区別し、実機への転送・描画を別途確認する。LCD の最終解像度と E-ink 向け１bit 変換後のプレビューで日本列島の海岸線が降水域と区別して明瞭に判別でき、実機完成後も同じ条件を満たすことを確認する。E-ink では降水強度の細部より降水域の位置・広がりを把握できることを確認し、黒ベタ表現も合格候補に含める。YouTube・風刺画のサブ機能ボタンは無反応でよい。ライブカメラは次期対象。
5. **AC-05** <a id="ac-05"></a> 複数端末・Web UI：ホームから各プラグインページへ入り、各ページからホームへ戻れること、メインとプラグインの API が同一ポート上で提供されることを確認する。下／次ボタンの通知から基盤の共通切替処理が選択状態を更新し、プラグイン指定の表示を基盤の送信手段で端末へ届け、論理状態更新と実表示完了を区別できることを確認する。複数端末の実機がそろった後は、端末 A のプラグイン選択・待機・切断が端末 B の選択や表示を巻き込まず、YouTube 視聴端末への動画変更はプラグインの指定どおり伝播することを別途確認する。Pico の通信で端末が自動登録され、初版 LCD 端末の初回は４機能 ON・共通初期順序・YouTube 表示になること、能力非対応のプラグインは理由を示して利用 ON にできず、E-ink の YouTube は制限付きで選択できること、端末 ID 別のプラグイン ON/OFF が Pi サービス再起動後も保持されること、前回プラグイン無効時の共通順序の先頭への切替と全 OFF 時の画面中央「PICO窓」・Web 設定操作、オフライン端末の状態表示と不要端末の削除を確認する。登録済み端末をオフライン中にも Web UI で設定でき、変更が再接続時に適用されることを確認する。端末別の接続・生存確認・２ボタン長押し設定は改訂・範囲・能力を検証し、未同期と適用済みを区別する。Pico は正常値を不揮発保存し、ネット接続前と破損時に組込み初期値で動作する。同期中も現接続を切らず、heartbeat 15 秒と Pi 側オフライン判定 45 秒の変更は新改訂の heartbeat 確認後に完了させる。オンライン端末の削除ではセッションが終了し、再接続時は一覧に再登場する旨を Web UI に表示することを確認する。削除済み device_id の再接続では旧端末固有設定（天気の地域を含む）が復活せず、対応可能な初期機能 ON・天気の初期地点が東京駅の新規端末として自動登録され、保存済みの共通順序が適用されることを確認する。削除によって端末側の Wi-Fi 資格情報やファームが消えないことも確認する。基盤が端末 ID・接続・選択プラグイン・表示能力・入力イベント配送と指定端末への描画手段を担当し、プラグインが内容・共有範囲・再生状態・送信先を決めることを確認する。基盤が同じプラグインの全端末へ同内容を強制しないこと、接続判定は Pi サービスの状態で行うことも確認する。Web/API と端末通信が自宅 LAN・Tailnet の設定済み宛先で利用でき、インターネットへ直接公開しない構成であることを確認する。PicoMado 独自の API キーや Web ログイン登録を要求しない。
6. **AC-06** <a id="ac-06"></a> 能力差：E-ink 端末完成後には YouTube を選択でき、低頻度・飛び飛びの表示を許容して動くことを別途確認する。初版 LCD １台の完成条件に E-ink の実機結果を含めない。端末能力に応じた間引きと Web 設定／ファーム能力の境界も設計・検証する。
7. **AC-07** <a id="ac-07"></a> 共通ビルド：採用した設定階層から端末 ID 別の出力と UF2 を生成し、成果物の取り違えや共通ソースの端末別コピーが起きないことを確認する。
8. **AC-08** <a id="ac-08"></a> 接続経路・異常：外出プロファイルでは SOCKS5 認証・Pi アプリへの到達・同じ Pico 起点 TCP 上の PUSH／ACK を確認する。自宅 direct TCP、長時間・動画・切断復帰は製品取り込み時に別途確認する。秘密値を Git に含めない。
9. **AC-09** <a id="ac-09"></a> 待機表示：E-ink 対応を実装する場合は、電源ボタンでの待機後に直前画像を保持し、画面をクリアせず、通知による更新も起きないことを確認する。LCD は黒表示を確認する。BLK 未結線時の物理消灯は合否対象から外し、結線後に項目２の OFF 制御を確認する。
10. **AC-10** <a id="ac-10"></a> YouTube 共有：複数端末の実機が揃った後、初期 YouTube プラグインが視聴端末間で動画と再生位置を共有し、端末ごとのプラグイン選択は独立することを確認する。A が天気へ移っても B は視聴を続け、A の再参加時は共有中の現在位置から表示する。動画変更は視聴中の全端末へ伝え、フレーム単位の同期を要求せず、遅い端末が他端末を停止させないことを確認する。将来、対応済み能力の範囲でプラグイン側に端末別再生状態を追加でき、基盤が全端末同内容を強制しない構造も確認する。
11. **AC-11** <a id="ac-11"></a> プラグイン Web 画面：基盤が共通枠と対象端末選択を提供し、プラグインが共通コンテンツと端末別設定の項目・処理を提供することを確認する。全端末共通の順序を変更でき、各端末では利用 OFF の項目を飛ばすことを確認する。操作の影響範囲を画面で示し、対象範囲はプラグインが決め、全端末への自動反映を基盤が強制しないことを確認する。端末別項目がない場合は無理に作らず、端末別プラグイン有効／無効という基盤設定とプラグイン固有の端末別設定を区別する。Web 共通設定の↑↓ボタンによる並べ替えと保存も確認する。
12. **AC-12** <a id="ac-12"></a> 事前更新と失敗表示：風刺画・天気・雨雲の１時間ごとのサーバ側取得・更新と、選択時の準備済み表示を確認する。保存済み取得データを利用し、最後の正常取得から１時間以上経過していれば直ちに再取得し、失敗した試行で鮮度判定の起点が更新されないことを確認する。天気の地域・対象日と雨雲の対象日時に取得データを対応付け、時系列を対象日時で管理すること、地域変更・日付切替に伴う必要データの無効化・再取得と旧設定で進行中だった取得結果の排除を確認する。保持範囲外になった表示対象日時の具体的な扱いは設計時に定めてから確認する。時系列素材の事前準備方式は設計時に選んで検証する。天気・雨雲では外部 HTTP 取得の各回 20 秒と追加２回を Web でプラグイン別に変更・保存でき、次の取得から反映することを確認する。再試行後も失敗すればそのプラグインのエラー描画になることを確認する。選択時の画面転送・物理更新をゼロ秒とは判定しない。
13. **AC-13** <a id="ac-13"></a> 状態競合：プラグイン切替後に旧プラグインの画像が届いても新画面を上書きしないこと、接続試行のキャンセル直後に接続完了が通知されても入力・接続状態が破綻しないこと、同一 device_id の再接続で新接続を有効にして旧接続を終了し、旧接続の遅延操作・応答・切断 callback が新セッションを変えないこと、待機直後の切断通知で待機画面や状態が意図せず変更されないことを確認する。
14. **AC-14** <a id="ac-14"></a> 通信・描画契約：分割受信、異常長・破損・タイムアウト、受信通知と描画完了通知の差、表示対象／フレーム識別を設計した契約に従って検証する。接続世代と表示世代を混同せず、旧画像や旧 ACK が現在の画面・セッションを変えないことを確認する。
15. **AC-15** <a id="ac-15"></a> 送信待ちと動画：端末別送信待ちの上限と古い未送信フレームの扱いを確認し、遅い端末が他端末の送信や YouTube プラグインの共有位置を止めないことを確認する。push 対応 LCD と E-ink の通常画像は送信中１枚・未送信最新１枚に制限し、描画 ACK 欠落で次画像の送信許可が止まらないこと、端末別の画素形式・更新方式と旧 LCD の ACK 契約が維持されることを確認する。ACK 非依存化を入力 TCP 欠落の解消とは判定しない。
16. **AC-16** <a id="ac-16"></a> 取得・設定：定期取得と即時取得の重複、正常取得後の鮮度、取得失敗後のエラー描画、同じ地域の端末間での取得再利用と端末別地域設定の独立、設定の原子的保存、接続設定移行中の遅延完了通知、ビルド時の ID 重複を設計した期待結果で確認する。
17. **AC-17** <a id="ac-17"></a> 視認性と観測性：全国雨雲地図の日本列島の海岸線を、最終解像度の LCD と E-ink 向け１bit 変換後に明瞭に判別できるか、端末状態・最終通信時刻・エラー種別をログと Web UI で追えるかを確認する。要件ごとに試験の期待結果と合否を対応付ける。
18. **AC-18** <a id="ac-18"></a> 非機能の測定：応答、接続復帰、動画 fps・遅延、長期安定、消費電力、他プラグインへの阻害を測る。合否閾値と測定期間は測定計画で決め、現時点で数値を固定しない。

## 優先度の低い Want：Bluetooth 音楽再生

**ユーザーの Want。** 所有する Echo Show 5 と第２世代 Echo を、Pico W と Bluetooth 接続するスピーカーとして使い、Web UI で接続先を指定したい。Web UI が機器選択・接続を制御し、Pico が音声を送信する構成を検討する。BTstack 公式の [A2DP Source デモ](https://github.com/bluekitchen/btstack/blob/master/example/a2dp_source_demo.c) と Amazon による [Echo／Echo Show の Bluetooth スピーカー利用説明](https://www.aboutamazon.com/news/devices/connect-alexa-bluetooth) は、この構成を検討する根拠となる。ただし、今回の Pico W と所有する Echo の実機接続、連続再生、Wi-Fi 動画との併用は未検証で、対応や安定動作を保証しない（U-16）。

Pico の A2DP Source → Echo の Sink を想定するが、音源、デコード分担、SBC 処理とバッファ、音画同期の要否、Wi-Fi との共存、Pico W の資源量、ペアリングと接続先切替の操作は未決。`/home/tane/dev/PicoW/` 配下の `pico-sdk`、`pico-examples`、`btstack` はユーザーが更新済みとの申告があるが、本書では中身を調査しておらず現在バージョンは推定しない。Bluetooth は初期受入の対象に含めない。
