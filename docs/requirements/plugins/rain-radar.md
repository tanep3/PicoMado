# 雨雲レーダープラグイン要件

[要件定義書の案内](../README.md)と[共通カーネル要件](../kernel.md)を参照する。共通の事前更新・鮮度・失敗表示・閲覧中セット保持は[プラグイン共通運用要件](../README.md#プラグイン共通運用要件)に置く。

## 内容・情報源・検証限界

天気とは別の独立プラグイン。日本列島の地図上で取得した降水域の時系列を表示し、事前更新は共通運用要件に従う。気圧配置を示す天気図とは別物。気象庁の高解像度降水ナウキャストを採用する。プログラムによるタイル取得・PNG 合成は実験済みで、海岸線の可読性改善と実機描画は要検証（U-10）。

**調査済みの公開例・製品未実装。** 気象庁の[高解像度降水ナウキャストの説明](https://www.jma.go.jp/jma/kishou/know/kurashi/highres_nowcast.html)と公開時刻一覧 [N1](https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N1.json)・[N2](https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N2.json)を Web で読み取り、確認時点では過去３時間・未来１時間の範囲だった。対象時刻のデータがそろう場合に１時間刻みで最大５画面とする案だが、将来もこの範囲が固定される保証はない。毎時取得したセット内の最新**観測**を既定画面とし、対象時刻と観測／予測の区別を表示する。PNG タイル本体の取得・プログラムによる合成プレビューは[雨雲描画実験](../../../experiments/jma-radar-render/README.md)で行ったが、海岸線の可読性は受入条件を満たしておらず、Pico 実機への描画は未検証（U-10、U-14）。画像生成に LLM は使用していない。さらに長い予測を別製品と混合する仕様は決めていない。

## 時刻別操作と視認性

デフォルトは取得セット内の最新観測時刻の雨雲表示とし、対象時刻および観測／予測の区別を画面に示す。下ボタンで１時間先、上ボタンで１時間前へ進む操作を基本とし、取得済みデータの端ではその場で停止して循環しない。日本列島の地図上に、実際に取得できた時刻の雨雲を描く。最新観測より先へ進むには予測データが必要で、予測がなければ初期位置からの下押下では進まない。取得元は気象庁の高解像度降水ナウキャストとし、確認時点の時刻一覧は過去３時間・未来１時間の範囲だった。対象時刻がそろう場合の１時間刻み最大５画面を設計候補とし、範囲を固定値として保証しない。実際の時刻一覧とタイルの取得・合成を実験プログラムで確認したが、端末描画は未検証とし、存在しない中間時刻の画像は作らない（U-10、U-14）。日本列島の海岸線は、最終表示解像度の LCD カラー画像と E-ink 向け１bit 変換後の両方で明瞭に判別できなければならない。E-ink 向け１bit 表示では降水強度の細かな表現より、降水域が日本列島のどこにどれほど広がるかを優先する。ただし降水域を一律の黒ベタに簡略化することは許容しない（2026-11-07 改訂、下記「E-ink 描画方式の決定」参照）。海岸線の明瞭性は必須とする。ここで示すのは雲全体ではなく降水域である。

E-ink の描画方式は 2026-11-07 に決定した。LCD フレームを輝度で閾値変換する方式（現行の `eink::from_lcd` 経由）は本プラグインの要件を満たさない。E-ink では 250×122 ネイティブに意味で描く：海・陸・観測範囲外はトーン（ドット密度）で区別し、海岸線はベタの線で描き、降水はその強度をドット密度の単調な階調へ写像する（弱い雨ほど疎、強い雨ほど密からベタ）。観測範囲外は斜線ハッチではなく一様な中間トーンとする。対象時刻・観測／予測の区別・クレジットの文字は、密度変換の後にベタ描きで重ね、網点化しない。輝度ベースの変換は、黄色・オレンジ等の強い雨が高輝度のために消失し、降水強度の順序そのものが壊れるため、いかなる二値化・網点化手法と組み合わせても採用しない。

## 取得の初期設定

外部 HTTP 取得は１回 20 秒でタイムアウトし、初回後に２回再試行する。タイムアウトと追加再試行回数は、このプラグインの Web 共通設定で変更・永続化できる。変更は次に開始する取得ジョブから使い、進行中の結果と新設定の取得セットを混同しない。再試行間隔は実測後に決める。

## サーバ初期実装の検証状況（2026-10-12）

Rust サーバに独立した雨雲プラグインを追加した。保存済み JMA 世代の N1/N2 時刻一覧、`hrpns` PNG、`hrpns_nd` 欠測域から、実在する１時間刻みの観測４時刻・予測１時刻を選び、全国の 160×80 RGB565 画像を生成する。最新観測を通常画面にし、模擬 WebSocket 端末で上下移動、両端停止、更新中の閲覧セット保持、取消し後の最新観測復帰を確認した。端末別取得世代を検査し、同じ JMA 取得元は１回の取得を端末間で共有する。取得失敗時は閲覧位置を保持したままエラー画像を出す。

海岸線を強調した LCD 合成と、白縁取りを考慮した 250×122・１bit の E-ink プレビューを Rust で作成した。E-ink 画像の端末配信経路、Pico 実機表示と視認性の受入、現在の JMA HTTPS タイル一式の実走試験は未完了。保存済み世代を使う自動試験の合格と、実機受入は区別する。

## E-ink 描画方式の決定（2026-11-07、RADAR-EINK-DENSITY-20261107）

利用者から「E-ink では何だか分からない」との報告を受け、変更 [RADAR-EINK-DENSITY-20261107](../../changes/RADAR-EINK-DENSITY-20261107.md) として調査と実測を行い、本書の E-ink 条項を改訂した。根拠の要約：保存済み JMA サンプルからリポジトリ自身の試験で生成した実フレームと、タイル内の実降水色８色（弱→強）について、現行の輝度閾値変換では弱い雨と黄色・オレンジ（強い雨）が消失し中間の青だけがベタ黒になる（ディスク濃度 0.00／0.00／0.99／0.98／0.00／0.00／1.00／0.78）。pic2gray4px を輝度画像へ適用しても順序の誤りは残る（黄色 0.12 ＜ 水色 0.20）。降水強度を灰色の濃さへ写像し直してから pic2gray4px の 2×2 セル変換を行う方式（方式 E）では 0.19／0.32／0.44／0.54／0.66／0.79／0.90／0.99 の単調な階調が得られ、実フレームへ仮想雨雲を配置した試験でも３つの雨域すべてが階調付きで残り、海・陸・観測範囲外がトーンで分離した。

この決定により U-10・U-14 の未決事項のうち「E-ink の描画方式」は解消する。受入条件 AC-04 の「黒ベタ表現も合格候補に含める」との文言は本改訂と矛盾したため、[要件 README](../README.md) 側の調整（v1.3）も同一の仕様コミットで行った。保存サンプルの５フレームはいずれも降水画素が約 0.5% のほぼ無雨であり、実データの雨そのものの検証は実色を用いた合成試験と仮想雨雲試験に依拠する。雨の多い実世代でのホスト確認と Pico 実機での視認性受入は未完了であり、方式の決定と実機の効果確認は区別する。
