# EINK-VIDEO-20261105

Status: production server now includes the folded video settings and 30-second limit; E-ink_0 has the measured 512-byte SPI burst firmware. LCD and E-ink_1 firmware remain unchanged.

## Requirements and existing boundaries

YouTube and local video should offer E-ink playback at a configurable 2 frames per second by default, with a configurable full refresh every 5 seconds by default. The E-ink_0 trial setting was later changed to 10 seconds. Intermediate E-ink frames use a partial refresh. The 2x2 cells produced by pic2gray4px are independent of frame rate. Do not add persistent E-ink frame files. Retain existing LCD playback, uploaded files, YouTube sources, historical selections, settings and existing converted JPEG caches required by LCD/history. Do not delete user data. Preserve one shared playback clock and per-device latest-frame admission; skip stale frames if conversion, transfer or panel drawing takes longer than 500 ms.

Current `playback.rs` reads one 160x80 RGB565 frame from existing converted JPEG files. `application_jobs.rs` sends those pixels to all targets. E-ink currently falls back to `eink::from_lcd`, then `display_eink.c` uses full refresh for ordinary video frames. Local video's `Plugin::supports` currently accepts LCD only and must be extended. Its partial refresh policy and `EinkRefresh` protocol are clock-only, measured in minutes. Firmware uses a 10 second BUSY timeout. pic2gray4px currently accepts file paths and writes a 1-bit PNG; its CLI has no stdin/stdout raw mode. The server must decode/pack the PNG into the existing 250x122 mono1, 3813-byte wire format. Existing converted JPEG cache is distinct from a new E-ink frame cache; this first implementation can reuse those JPEGs as source, accepting their 160x80 resolution limit. A later source-video decoder can improve E-ink image quality without changing the wire contract.

## Design and implementation

Add per-device E-ink video settings with revision/validation (fps 1..5, full interval 1..60 seconds, defaults 2 and 5) through the existing plugin-device configuration API for YouTube and local video, with a Web control for each E-ink device. Advertise a new E-ink video partial capability; old firmware continues receiving full-refresh frames at a conservative cadence. Extend the frame header with separate E-ink video refresh metadata so clock minute semantics remain unchanged. Firmware tracks the full-refresh epoch and permits partial updates only after a completed base frame and while display identity is unchanged; the 5-second default may request about 9 partials at 2 fps; the E-ink_0 10-second trial may request about 19. Both exceed the vendor recommendation of five. Do not silently claim compliance. Full refresh should start no more frequently than the configured interval; frame admission still depends on BUSY completion, with late frames skipped.

For E-ink viewers, read a required JPEG frame outside the application lock, fit/crop it to 250x122, run the upstream pic2gray4px CLI in a private temporary directory, validate the output PNG dimensions/length, pack to mono1, publish to bounded latest-only slots, and remove temporary files on success or failure. Recover stale private work directories on startup by ownership/age checks. Limit simultaneous CLI conversions and child runtime, kill/wait on timeout, and never return an old generation after selection changes. A shutdown can wait for the conversion's 2-second bound. Share the converted mono1 frame among E-ink devices viewing the same sequence. Preserve LCD's original read/publish path.

The implementation serializes conversion in the shared playback loop, limits the CLI to 2 seconds per frame and backs off for 5 seconds after failure. It uses the installed CLI beside the server binary or the explicit `PICOMADO_PIC2GRAY4PX` path. A missing CLI leaves the last E-ink frame visible and produces a bounded server log message. No converted E-ink frame is stored persistently. A source frame is loaded once and its converted mono1 bytes are shared among all E-ink targets in that playback offer. The latest-slot sender replaces frames that arrive before the panel is ready.

For a 6 fps source, a 5-second full-refresh interval is represented by 30 source-frame positions. E-ink sends at most 2 of those positions each second. The first image after a display identity change is full; subsequent frames are partial until the next 30-position boundary, with overdue positions skipped. An old E-ink firmware without `eink-video-partial-v1` receives full images at the configured interval. The source JPEG remains 160x80; resizing it to 250x122 cannot restore detail lost during the earlier LCD conversion. This can be improved later without changing the wire format.

## E-ink drawing bottleneck and safe next steps

The same USB trace labels `spi_end` with 4000 bytes for partial updates and 8000 bytes for full updates. For 25 matched partial frames, SPI preparation/write took a median 0.179 seconds; the time from SPI end through the panel BUSY completion and render ACK was 0.600 seconds. For the two matched full frames, these stages took 0.364 and 2.284 seconds at the median. The 4 MHz SPI clock has an ideal data-clock lower bound of 0.008 seconds for 4000 bytes or 0.016 seconds for 8000 bytes, but the existing driver writes one byte per GPIO/CS toggle and polls in 128-byte chunks. Its roughly 0.18/0.36-second write duration is therefore a plausible software overhead target. The observed 0.60/2.28-second post-write interval is dominated by controller BUSY and visible waveform time. The trace does not independently isolate controller waveform time from BUSY detection or the reset/initialization before SPI; the latter also includes time queued behind prior panel work. The firmware code requires at least 1 ms before partial SPI and at least 20+2+120+10 ms of staged full-reset waits, plus BUSY checks.

A candidate optimization is a bounded SPI burst for the existing 4000-byte RAM plane, at the current 4 MHz setting and without changing controller commands, reset timings or waveform. It would require host tests of command/data framing and an additional, separately authorized E-ink_0 build/flash and visual comparison. Even eliminating most of the measured 0.179-second write time would leave roughly 0.6 seconds of BUSY/waveform work, so 2 fps is not established as achievable on this panel. Increasing SPI clock, altering waveform/LUT or shortening BUSY waits are not justified by the present trace; the [Waveshare V4 panel specification](https://files.waveshare.com/upload/4/4e/2.13inch_e-Paper_V4_Specification.pdf) says BUSY is high while outputting the display waveform and recommends a full refresh after five consecutive partial/fast refreshes to limit afterimages. The 10-second user setting trades fewer full flashes for more partials and should be judged by visible ghosting. No new flash or server restart was performed for this analysis.

The new video-page layout uses a native closed `details` and `summary` directly above each page's history. A real headless Chrome load of the updated source against read-only production API responses verified both YouTube and local-video DOM order, closed initial state and summary presence. The script passed `node --check`. The per-device API write and readback set E-ink_0's two plugins to 10 seconds at revision 2, while preserving 2 fps; other devices' settings were not changed. The source-only UI change still requires a server restart before it appears on the production page. A read at 17:48 JST found E-ink_0 YouTube settings subsequently at 5 fps / 20 seconds (revision 4) and local-video still at 2 fps / 10 seconds (revision 2); this work did not overwrite those newer values.

At the later observed 5 fps / 20-second YouTube setting, a separate 15-second USB sample contained 74 CRC-complete received frames (4.74 fps over the sample) and 19 render completions (1.24 fps). The median receive gap was 0.208 seconds and median render gap 0.804 seconds. Raising the requested rate increased received/ignored frames but did not raise panel throughput toward 5 fps. The first `frame_start` trace record was stale relative to the capture window, so the receive-rate calculation uses CRC-complete records.

## SPI RAM burst experiment (source and host only)

The original V4 driver wrote each of 4000 RAM bytes with its own D/C and CS toggles and one-byte blocking SPI call. Keep the existing 4 MHz clock, command sequence, update mode, waveform, BUSY deadline and full/partial selection, but write each RAM chunk as a single SPI burst with D/C high and CS low throughout. The final trial uses up to 512 bytes per poll, replacing 4000 byte transactions with 8 chunk transactions on a partial frame. The 4 MHz wire-time lower bound is about 8 ms; the previously measured 179 ms RAM-write phase leaves at most about 171 ms to remove, and the measured 600 ms post-write BUSY phase remains. Thus even an ideal RAM transfer would leave at least about 0.6 seconds plus scheduling and other commands; a stable 2 fps cannot be promised. Host tests must verify exact RAM bytes, command/data framing, full old/new RAM, partial mode, trace ownership, and timeout/recovery. Physical speed, visible artifacts and panel tolerance require measurement. No SPI overclock or waveform/BUSY shortcut is included.

The source experiment implements this 128-byte burst in `display_eink.c`; the E-ink host fake checks burst bounds and RAM payload equality. Targeted E-ink host tests passed with and without tracing, including full/partial RAM, pending identity, timeout and recovery. The complete `firmware/tests/run_host_tests.sh` suite also passed. No UF2 was flashed; therefore the projected savings remain unmeasured on a physical panel. The current running firmware still uses byte transactions.

The first E-ink_0 test flash of the 128-byte burst passed picotool write verification and the device returned, but the USB trace showed about 0.17 seconds between `spi_begin` and `spi_end` for 4000 bytes, scarcely changed from the former ~0.18 seconds. The 128-byte-per-poll limit still schedules 32 chunks across main-loop polls and dominates that phase. Revise the experiment to bounded 512-byte bursts (8 polls for 4000 bytes, about 1 ms of 4 MHz wire time per poll), retain all other panel operations, rerun host/build gates, then reflash the same identified E-ink_0 and measure. The 128-byte build was not measured for visual quality, so no improvement claim is made from it.
