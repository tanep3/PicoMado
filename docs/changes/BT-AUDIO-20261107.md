# BT-AUDIO-20261107 — PicoMado Bluetooth audio / remote input

## 目的と境界

PicoMado の Pico W から Bluetooth Classic スピーカーへ A2DP 音声を送り、AVRCP の操作を端末入力として使えるようにする。マイク/HFP/SCO は本変更の対象外で、別の PicoW_Bluetooth_lib 調査を待たない。PicoMado を母艦 Bluetooth のリモコンに置き換えるものではない。

ユーザーの仮説は「ライブラリ完成を待たなくても、A2DP と AVRCP を PicoMado に実装できる」。BTstack を直接利用する独立 adapter とし、未完成ライブラリをコピー・内包しない。別リポジトリの実証は比較材料として使う。配布用依存を新たに導入する場合は別途明記する。

## 現状の根拠

- 調査開始時 PicoMado 正本 main: `b5a2c16`、作業ツリー clean。
- 既存 Want: `docs/requirements/README.md` の Bluetooth 音楽再生。Web UI から接続先指定、Pico が音声を送る方向。
- PicoW_Bluetooth_lib の `docs/evidence/2026-11-07-a2dp-player-hardware.md` に、LBSで48kHz・440Hz・3秒の再生と明示再接続の実聴取あり。同文書で AVRCP、長時間、Wi-Fi共有runtimeは未検証。
- PicoMado は `pico_cyw43_arch_lwip_threadsafe_background` を使用。別ライブラリの単独runtimeをそのまま起動して二重所有させない。
- 端末の既存入力は `pm_operation` と `perform_operation` に集約され、0ボタンのE-inkでも論理入力経路を持つ。

## 採用する責務分割（設計案）

1. **Bluetooth adapter**: Pico SDK/BTstackを所有する薄いC adapter。初期化・GAP・SDP・A2DP Source・AVRCP Target・SBCエンコードを担当。CYW43は既存初期化を共有し、二重init/deinitしない。callbackから表示/ネット送信/ファイルIOを実行しない。
2. **AudioSession aggregate**: 有界の接続/再生状態、世代、エラー、PCMキューを所有。Query→純粋な遷移→adapter effectとする。接続失敗や未接続が表示や物理入力の進行を止めない。
3. **Server audio executor**: 音源の取得/デコードは母艦側。音源プラグインは再生意図を提供し、共通層へプラグインID分岐を増やさない。既存動画から音声を得る実装は共通音声配送が成立してから行う。
4. **Remote input adapter**: AVRCP pass-throughを有界イベントへ変換。既存の端末入力APIを呼ぶ。GPIO数によって無効化しない。AVRCPが接続したこととボタンが届いたことは別の検証項目。

## Web UI と端末別接続の必須契約

ユーザー追加要件：複数のPicoMadoが各々別のBluetooth機器へ接続する。Web UIホームの各端末設定から探索→候補選択→ペアリング、ON/OFFを操作できるようにする。

- 入口は既存 `service/src/ui.html` のホーム端末カード内。共通設定や音源プラグインのページへ混ぜない。
- 探索は母艦ではなく選択したPicoが実行する。候補にはその探索世代の名前・アドレス・対応情報を表示し、別端末/古い探索結果を混ぜない。
- 端末別のdesired state（有効/接続先）とobserved state（探索中/ペアリング中/接続済み/失敗）を分離。ボタンを押しただけで「接続済み」にしない。
- ONは保存済み接続先への接続を開始できるが、未選択の機器へ勝手にpairしない。OFFは探索・接続・音声を停止、接続情報の削除と区別する。
- ペアリング鍵をUI/API/logに出さない。保存する場合は端末側の既存flash領域との競合・原子性・消去範囲を設計する。Wi-Fi資格情報の領域を上書きしない。
- 設定更新は既存のdevice incarnation/revisionを利用。探索/接続の一過性操作はcommand ID/期限/セッション照合を持ち、再接続時に旧コマンドを再実行しない。
- オフラインではON/OFF等の希望設定保存と、実行できない探索/ペアリングを区別する。Bluetooth非対応ファームには実行ボタンを出さず、必要な更新を案内する。
- 1台が別機器を使っても他端末の候補・接続・再生を変更しない。同一スピーカーの同時利用は保証せず、機器側拒否を正しく表示する。
- UI回帰：探索連打、OFF/キャンセル、途中切断、設定競合、古い応答、機器名のHTML表示、2端末同時操作、0ボタンE-inkを含めて検証する。

## 段階と受入

### A: 音声配送に依存しない端末統合

- 初期値はBluetooth無効。既存LCD/E-inkビルドの通信・表示挙動を維持する。
- 実験ビルドで既存Wi-Fi接続/表示を保ったまま、明示接続した相手へ有限テスト音を再生する。これを音源プラグイン完成と呼ばない。
- AVRCPのpress/releaseを区別し、同一pressの重複を除去。未知/非対応命令は拒否し、誤ってPOWERへ変換しない。
- 操作の候補はNEXT→DOWN、PREVIOUS→UP、PLAY/PAUSE→SUB。POWER、STOP、音量の流用は自動採用しない。初期割当は実機操作性の検証対象とする。
- 接続/切断/再接続、途中キャンセル、音声underflow、満杯、古い接続callbackをhost試験。実機ではLCD/E-ink・Wi-Fi共存・AVRCP各ボタンを確認する。

### B: 母艦からの実音声

- 音声のフォーマット/サンプル位置/世代を表示frame tokenと混同しない。
- capabilitiesで交渉した端末だけに配送。旧端末へ新しい音声messageを送らない。
- PCM候補は16bit LE stereo/48kHz（192kB/s）。端末は小さな有界buffer、SBCはPicoで生成し、再生時計はBluetooth送信側に置く。実機負荷に応じ母艦SBC方式との比較を行う余地を残す。
- 音声は画像のlatest置換を使わない。世代と連続sample位置を検証し、欠落は明示的なunderflow/再同期とする。無期限bufferは禁止。
- 初期は独立した音声ストリームの有限試験を先に行い、動画と音声の同期・競合/優先度・一時停止/再開の契約を定めてからYouTube/ローカル動画へ接続する。
- 設定はdevice単位。接続先・接続状態・失敗状態をWeb UIで表示する。詳細理由の表示は今後の改善対象。他デバイスの音声や表示へ影響させない。

## 実装記録（2026-11-07、実機適用前）

- `bluetooth_runtime.c` は既存CYW43 async context上でSDK A2DP Source/SBC encoder/AVRCP Targetを使う。PicoW_Bluetooth_libのコピーやリンクは不要。音声は48kHz stereo signed16 little-endian、最大2048 PCM frames。AVRCP初期割当はNEXT→DOWN、PREVIOUS→UP、PLAY/PAUSE→SUB。未知操作・音量・POWERはアプリ操作へ変換しない。
- SDKのAVRCP Targetはcallback前にプロトコル上のACCEPTを返すため、非対応操作はアプリ側で無作用にする。SDKパッチは加えていない。
- wire kind20/21はBluetooth制御/観測、22/23は音声開始/停止、24はPCM binary、25は累積accepted/consumed、26はEOF。incarnation/session/display/streamを照合し旧streamを拒否。creditを累積位置で管理し再送や古い通知で容量が増えない。最終SBC blockのみ最大127framesの無音を足し、EOFとunderflowを区別する。
- ローカル音楽プラグインとの共通 `AudioPlaybackSpec` / `read_audio` を利用。YouTube・ローカル動画の音声抽出とAV同期はまだ接続していない。ネットラジオは今後同じ音声契約へ追加できる。

- `PM_BLUETOOTH_AUDIO=ON` のみ新経路を組込む（実機未検証のため既定OFF）。ON版は現行の `frame-bytes-v1` binary画像配送を前提に旧numeric-array JSON作業領域を縮小、画像画素・保持枚数は削減していない。OFF版の旧JSON容量は維持。

## 実機適用後の無音調査（2026-11-07）

ユーザー承認によりサーバを更新し、登録Flash IDと一致するLCD `E661640843239D21` にBluetooth有効ファームを適用した。LBSへの接続、サーバ画像描画ACK、PCM受信、48kHz交渉までは実測で確認したが、ユーザーから無音を指摘された。音源は保全した。

- SDKのSBC encoderは初回encode前のpacket lengthが0。encode後に長さを読むよう修正し、実SDK encoderをhostへリンクした試験で0→119bytesを確認。
- USB実測: `accepted=2560 consumed=640`、`status=0xff02 d1=-103 d2=3 d3=640`。受信PCMが残っているのに、1 SBC frame/packetの送出で100ms遅延停止になっていた。交渉rate不一致や音源変換失敗ではなかった。
- SDK source exampleを参考にMTU内で複数SBC frameを集約。48kHz/119byteなら7frames=896samplesを1RTPへ格納。初回送信成功を時計起点にし、以後時計は巻き戻さない。1回1packetで追従、250ms超は明示停止。PCM欠乏は最大50msのみ待つ。実機の連続再生は引き続き検証する。
- サーバと端末に開始・初回受領・消費・失敗を識別する限定ログを追加。音源名・本文は記録しない。正常進捗は端末で最大1秒1回。
- サーバ更新前の実行ファイル/設定/SQLite安全バックアップ/素材、LCD旧UF2を私的に退避した。pushなし。独立検証・最終クローズは未実施。

- 続く再試験では `AudioStart sent` 後に端末受領0のcredit timeoutも再現。writerの画像分岐は`yield_now()`を待つため、同じselectでreadyな音声tickが先行し、新display世代のAudioStartがFrameStartより先に届きうる。新stream開始前のみ、同一DisplayTokenのReceiptAckを境界に待機するよう修正した。表示完了ACKは待たず、既に確立したstreamのPCM送出は描画に依存させない。現在世代照合・旧ACK排除・invalidate時の受領状態消去を自動試験で検証する。

順序修正後の実機では `audio_wait_display`→`audio_start_sent`→`audio_first_credit accepted=256`、LCD `begin ok=1` を確認した。これにより受領0の開始競合は解消した。一方、7frame集約でも `accepted=17920 consumed=16640 status=0xff02 d1=-261 d2=6 d3=16640` を観測し、約0.35秒分の音の送信で約261ms遅れる別の実時間性能問題が残る。連続再生を成功とは扱わず、packet cadence/共有runtime/codec負荷を継続測定する。

測定専用版の実測ではLBSのmedia payload MTUが704bytes。bitpool53のSBC119bytesでは1RTPに最大5frames（13.3ms分）だった。31packets/17280frames時点で、can-send待ち累計358ms（最大44ms）、encode累計125ms（最大5ms）、timer遅延累計49ms（最大3ms）。送出可能間隔とencode費用がpacket内音声時間を上回るため、次比較は許容bitpool範囲内の32とMTU最大集約とする。SDK/チップのSCO問題とは別件である。

次の比較版はSBC bitpool32をpeerのmin/maxへclampし、計算したframe長を初回から使う。LBSのMTU704では9frames/694bytes/24msとなる。最大15frames/40ms、遅延250ms停止、PCM待機50msの有界性を維持する。policy・SDK実encoderの9frame境界試験、LCD/E-ink ARM buildが成功。音質と送信頻度のtradeoffであり、実機再生結果を確認するまでは最終方式とは断定しない。

再起動後のLBS自動再接続失敗も調査対象に追加。`status=0x000b` はSDKのACL_CONNECTION_ALREADY_EXISTSで、鍵不一致ではない。SDKのflash TLV link-key DB初期化は有効。現adapterが成功incomingでもCID不一致で切断し、同一desired peerの自動接続を拒否し得る点を確認した。desired peer一致/有効状態/現在世代を厳格に確認したincoming所有権の引継ぎと、旧outgoing失敗callbackによる新CID破壊の防止を修正する。0x000bだけを成功扱いしない。鍵保持そのものの再起動後実機検証は別に残す。

bitpool32でも31packets/29056frames（平均7.3 SBC frames）で停止。満量9framesを待たず届いたPCMから小パケットを送るため集約が崩れていた。通常は満量を待ち、明示EOFが全量届いた時だけ短い最後のpacketを許す。初期prefillは2048frames、1792では開始しない試験を追加した。

既存動画経路との比較で、音声単独はmain loopが静止画扱いの2messages/5ms sleepだった。SBC割込み処理と重なり受信余裕が不足し得るため、音声active時のみ既存動画と同じ有界8messages/1msへ変更。動画・音声OFFの静止画経路は維持。LCD/E-ink ARM build成功、実機連続再生結果待ち。

満量集約+1ms版ではcan-send待ちは累計4msまで減少したが、PCM補充待ちが残り、23packets/26496framesで遅延停止した。サーバのread futureをAudioCreditが到着するたびdropしていたことを確認し、creditは同じread futureを保持したまま適用し、停止/切替のみ中断するよう修正する。また本番host listenerはSO_SNDBUFのみ設定しTCP_NODELAYは未指定だった（端末側は指定済み）。小PCM packetのNagle/delayed ACK待ちを避けるためTCP_NODELAYを明示し、実TCP socketで有効化を試験する。各要因の実機改善効果は次の再生で確認する。

ユーザーの実聴では「ラの音は聞こえたが電話のベルのように細切れ」。A2DP出音は確認できたが連続性の受入条件は未達。2048frames（42.7ms）のbufferでは24ms packet消費後の補充余裕が少ないため、4096frames（85.3ms）比較へ進む。新capability `audio-buffer-4096-v1` のcurrent online sessionだけserver windowを4096にし、旧端末は2048を維持する。容量変更はstream非稼働時のみ。LCD BSS235692bytes（+8192）、BSS後heap limitまで20132bytes。初期prefill4096・overflow・短EOFのhost試験成功。serverとfirmwareを揃えて配備する。

### Volume safety finding after real-music test

User reported that the real music was unexpectedly loud at night. The quiet synthetic test tone did not establish a safe real-track playback level. Current implementation sends decoded PCM without gain reduction; local-music/WebUI has no volume setting, and AVRCP handling supports only PLAY, PAUSE, FORWARD and BACKWARD, not volume operations or absolute-volume synchronization. LBS physical-volume-button behavior has not been measured and must not be assumed.

Parent instructed no further automatic playback until explicit confirmation. During the read-only check the state was playing; pause was applied and playing=false confirmed. Preserve audio files. Proposed safe correction: device-specific software PCM attenuation before transport, initially muted or conservatively low with explicit user enable, 0–100 bounded control, no gain >1, saturating arithmetic, boundary tests, and no autonomous audible validation. Silence/digital gain cannot guarantee acoustic SPL because LBS hardware amplification is unknown. Do not claim a safe loudness from a percentage alone. Actual implementation awaits scope selection.

## 2026-11-08: AVRCP専用media inputと物理Subの分離（実装前契約）

Welcome/ACTIVE and a current Bluetooth command. SDK BTstack setup and selection
of the BT-capable WLAN image occur earlier in shared CYW43 initialization. SDK
`wifi=JOIN` means associated, not still joining. ACTIVE/READY do not prove continuing
TCP ACK progress. Runtime OFF/stop does not imply HCI_POWER_OFF; an initial stop
currently initializes the controller. The saved 134153/134353 USB captures have no
precise command-receive/HCI-start marker. Server `connecting` is command intent,
not a device-received observation.

### Scope and decision table

Add `PM_BT_STARTUP_DIAGNOSTIC`, default **0**. CMake and C accept only 0, 1, 2.
Mode0 compiles out this diagnostic and preserves ordinary behavior. Mode1 is
observation A with existing start timing. Mode2 is observation plus bounded ACK
wait B. Both modes use the same fixed-size, main-loop log adapter and captured
MCU monotonic-millisecond timestamps. BT-disabled builds keep the no-op path.
No SDK, radio firmware, TCP/ARP policy, server protocol, timeout, audio or settings
change is included.

For mode2 only, before the first application runtime initialization:

| Input | Decision |
| --- | --- |
| No current pending command | Do not initialize; no autonomous command generation. |
| Stop before initialization | Cancel pending startup immediately and report successful no-op stop; do not power HCI to stop it. Already-initialized stop remains unchanged. |
| New generation/command, incarnation/session change | Discard old gate progress. Never inherit another command's permission to start. |
| Not ACTIVE, TCP not READY, IP not UP, missing PCB, or connection change | Reset ACK/wait evidence; no initialization. |
| First valid snapshot for this connection | Capture ACK baseline, not progress. |
| Forward ACK change on the same connection | Start a 5000ms wait once; use modular TCP sequence comparison, reject ambiguous/regressive movement. |
| Same identity/link, elapsed >=5000ms, `lastack==snd_lbb`, no unsent/unacked | Permit one existing initialization attempt; existing HCI-ready/stop/connect sequence follows. |
| Earlier, ACK fixed, or queued/unacknowledged data | Return without blocking main; display/input/network continue. |
| Received-time age >=25000ms | Existing failure/stop path; do not initialize or extend the deadline. |

Use a small pure gate with explicit snapshot values. The main-loop adapter owns
sampling under the existing network API, at most once per100ms while first-start
is pending. Do not use log visibility, USB attachment or DTR as a gate input.
Events log command acceptance, wait/progress/open/reset/cancel/expiry and actual
HCI power-call begin/return/working times. Runtime callbacks only capture fixed
values; formatting/output occurs outside the shared CYW43 lock. Identity is bound
to incarnation/session/generation/command and connection without keys or payloads.
Cap diagnostic text at a fixed boot-lifetime record count, expose suppression,
and use existing trace queue/drop accounting. All lines fit its144-byte limit.

The controller's first power-on markers survive command replacement in a separate
first-start identity, so a late working event is not assigned to a newer command.
Do not introduce sleeps, unbounded queues, repeated startup, or unrelated recovery.
SDK common initialization/WLAN-image selection are **not delayed** by mode2.

### Deadline and interpretation limits

The host token expiry uses another monotonic clock. Keep it echoed, never compare
it with MCU uptime and never refresh either deadline. Host has30s from issue;
firmware has25s from receipt. A transit-delayed command can already be expired at
the host, and extra local waiting can consume its remaining host budget. This
diagnostic does not prove host freshness and must not turn stale reports into
success. Record command age at gate release. If stable ACK conditions cannot be
reached before the local bound, retain a no-HCI/expired trial, not a successful BT
trial. A future alternative would withhold issuance at the host until a verified
stable interval and then issue a fresh generation, but that is outside this change.

A/B compares cold starts on the same device/image options/server/AP/profile/target
and stopped audio, changing only mode1 versus2. Measure the entire boot including
stalls before HCI, achieved HCI start delay and periods where the gate never opens.
Waiting for an independently recovering TCP connection is not proof that delaying
BT repaired it. Instrumentation/sampling cost and RF behavior require real-device
evidence. Flash/reboot/USB/server/network operations remain separately authorized.

## 2026-11-08: E-ink_1 HOME static-ARP control (specification before implementation)

The user authorized the proposed temporary same-device HOME-only static-ARP
comparison. The original Wi-Fi/BT startup hypothesis stays in this record.
Startup A, no-HCI B, and same-device compiled-BT-OFF all retained intervals in
which the ACK position for device-sent bytes stopped advancing. BT startup and
BT inclusion are not necessary for this failure class; an incidence/amplification
effect is still untested. A later ordinary BT-ON start recovered early.

The observed server IPv4 sometimes resolves to the router MAC and later to the
known host MAC. Router-MAC snapshots also occur during successful ACK progress;
actual-host-MAC snapshots can precede recovery. This is a correlation, not proof
of the cause. This control tests the mapping selected by the device's ARP cache.
It does not distinguish device data not arriving, host ACK not being generated,
or the returning ACK not arriving without corresponding packet evidence.

### Scope and lifecycle

- Add `PM_HOME_STATIC_ARP_DIAGNOSTIC`, default OFF and allowed only for the
  E-ink_1 build. The normal build compiles out all policy, state and new calls.
  No private configuration, SDK source, persisted settings or host networking
  changes are included. BT remains ON with startup diagnostic0.
- The main connection owner passes the current explicit profile identity to a
  diagnostic-only network entry point. Only device E-ink_1, profile HOME, direct
  non-SOCKS server `192.168.0.120` may install MAC `2c:cf:67:11:72:f3`. HOME2,
  AWAY, unknown profiles and other devices never install an entry. Log skipped
  profiles per connection without credentials. HOME with a different server
  is outside the fixed mapping and must not silently masquerade as a fixed trial.
- Use the installed SDK's actual option `ETHARP_SUPPORT_STATIC_ENTRIES=1`
  (not `LWIP_ARP_STATIC_ENTRIES`) consistently for all target/SDK compilation.
  Validate an UP/link-UP IPv4 route with assigned local address, nonzero mask,
  and the server on that local subnet. Reject off-subnet/gateway routing,
  missing routes and invalid HOME scope without creating a TCP connection.
- The network aggregate owns the temporary entry. Under the existing
  `cyw43_arch_lwip_begin/end` lock, remove any previous owned entry, install via
  `etharp_add_static_entry`, and read back the intended MAC before allocating
  or connecting the next TCP PCB. Installation/readback failure fails the trial
  connection, never silently falling back to dynamic ARP. No TCP packet may be
  sent in the remove/reinstall gap.
- `close_unlocked` retires the owned entry after retiring the old TCP owner;
  repeated close is harmless. Retry reinstalls before the next TCP connection.
  Profile change, standby and Wi-Fi restart already pass through this close
  boundary. SDK netif cleanup may remove the entry first; a missing/nonstatic
  removal result is recorded and is not permission to remove unrelated entries.
  No flash persistence or SDK-global cleanup is added.
- One bounded marker per connection reports fixed/skip/failure and profile,
  connection identity, MCU milliseconds and SDK result. Successful fixed marker
  includes the read-back mapping. Removal has a separate bounded marker.
  Ordinary TCP snapshots retain their existing meaning.
