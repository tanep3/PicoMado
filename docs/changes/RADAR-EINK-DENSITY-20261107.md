## Cause and measured evidence

The user reports that the rain radar reads acceptably on LCD but is unintelligible on E-ink ("E-inkだとなんだかわからない"). The shipping E-ink path for radar is the generic fallback: `application.rs` composes the 160x80 RGB565 LCD frame and `eink::from_lcd` fits it into 250x122 with nearest-neighbour sampling and a single luminance threshold (>= 128000 of 299r+587g+114b). Radar does not override `ContentPlugin::eink_frame_for`. A native-stroke prototype, `render_eink_preview`, exists in `radar.rs` but is not wired to devices and draws every wet pixel as the same solid black as the coastline.

Host experiments on 2026-11-07 (saved JMA sample `assets/jma-radar-20261012.json`, frames generated by the repository's own radar test) measured the disc darkness (0 = invisible, 1 = solid black) of the eight real precipitation colours found in the JMA tiles, weakest to strongest (242,242,255 / 160,210,255 / 33,140,255 / 0,65,255 / 250,245,0 / 255,153,0 / 255,40,0 / 180,0,104):

- Current `from_lcd` threshold: 0.00 / 0.00 / 0.99 / 0.98 / 0.00 / 0.00 / 1.00 / 0.78. The weakest rain vanishes, mid blue becomes solid black, and yellow and orange (heavy rain) vanish completely. The intensity order is destroyed.
- pic2gray4px applied to the luminance image: 0.02 / 0.20 / 0.53 / 0.74 / 0.12 / 0.34 / 0.61 / 0.59. Every level becomes visible and the map gains sea/land tone separation, but the order still lies: yellow (0.12) reads weaker than light blue (0.20), because yellow is a high-luminance colour. No luminance-based conversion can fix this; it is an isoluminance problem, not a dithering problem.
- Semantic remap then pic2gray4px ("method E"): 0.19 / 0.32 / 0.44 / 0.54 / 0.66 / 0.79 / 0.90 / 0.99. A clean monotonic ladder.

A second experiment placed three virtual rain systems (a strong cell south-west of Kyushu, a band crossing Honshu, a weak cloud near Hokkaido) on the real saved LCD frame. Under `from_lcd`, the strong cell shrank to its red core, the band flattened to a solid ellipse and the weak cloud disappeared. Under method E, all three survived with graded density, and sea, land and the no-data region separated by tone. Known weaknesses of the experiment output: header and credit text speckled because text was dithered together with the map, and the no-data diagonal hatch of the LCD source left a faint texture because the source was classified from the LCD frame instead of being drawn natively.

All five saved sample frames are nearly rain-free (about 0.5 percent wet pixels), so rain behaviour on real data rests on the synthetic tests with real tile colours plus the virtual-cloud test. Physical panel appearance is unverified.

## Requirements and existing boundaries

The plugin requirements [rain-radar.md](../requirements/plugins/rain-radar.md) currently require coastline clarity on both LCD and the E-ink 1-bit rendering, prioritise the position and extent of the precipitation area over fine intensity detail, explicitly permit simplifying precipitation to uniform solid black, and leave the drawing method undecided (black fill, white outline and halftone all candidates). AC-04 likewise includes solid black as a passing candidate, and U-10/U-14 record the E-ink drawing method as undecided.

The measured evidence above contradicts the solid-black permission: uniform black (whether from the threshold fallback or from a binary native render) destroys the intensity order and merges rain with coastline strokes. This change therefore revises the specification before any implementation:

- [rain-radar.md](../requirements/plugins/rain-radar.md) is revised (see the revision note in that file) to fix the E-ink method: a native 250x122 semantic rendering in which precipitation intensity maps monotonically to dot density, sea/land/no-data are separated by tone, coastlines stay solid strokes, and text is drawn solid after the density conversion. Luminance-threshold conversion of the LCD frame no longer satisfies the requirement for this plugin.
- AC-04's acceptance wording (solid black as a passing candidate; intensity detail secondary) is adjusted in the same specification commit as this registration (requirements README v1.3): solid black and luminance-threshold conversion are now failing candidates, and the U-10/U-14 row records the drawing method as decided.
- The U-10/U-14 undecided item "E-ink drawing method" is decided by this revision; real-device rendering and coastline acceptance under U-10 remain open.

Boundaries retained: the LCD RGB565 path and its frames do not change. The E-ink wire format stays 250x122 mono1 (3813 bytes); no firmware change is expected. No persistent E-ink frame files are added. Missing hours are never fabricated. The hourly pre-fetch, freshness and failure behaviour stays with the common plugin operational requirements.

## Design (method E)

Radar implements `ContentPlugin::eink_frame_for` and renders the E-ink frame from the same fetched tile data as the LCD frame, at native 250x122:

1. Build a grayscale canvas by meaning, not by colour luminance: sea a light grey, land a lighter grey, the no-data region a flat mid tone (drawn as tone, not as the LCD diagonal hatch), coastlines as dark strokes, and precipitation mapped from its JMA colour class to a fixed grey ladder ordered by intensity (weak = light grey, strong = near black). The ladder used in the experiment (205 / 175 / 145 / 115 / 85 / 58 / 30 / 8 over a sea grey of 228 and land of 246) is the starting point, to be confirmed against the tile colour classes in the design stage.
2. Convert the canvas to 1-bit with the pic2gray4px 2x2 cell method, following the server's established pattern of invoking the installed CLI (as for E-ink video and local images) during the hourly generation, not per device request. Conversion parameters must keep the grey-to-density mapping calibrated: the experiment used CLI defaults and produced a monotonic ladder, but automatic contrast/unsharp are photo-oriented; whether to fix them off for this synthetic input is a design-stage decision to be recorded with its own comparison.
3. Draw the valid-time label and the credit text as solid strokes after conversion, reusing the existing glyph painting, so text is never dithered.
4. Pack to the existing mono1 wire format. `render_eink_preview` is superseded as the design basis; it may be removed or kept as a test fixture only if the design stage says so explicitly.

Fallback: if conversion fails at generation time, keep the previous generation's E-ink frame and follow the common failure display rules; do not fall back to `from_lcd` silently, because that path is the defect being removed.

## Verification plan

- Golden tests on the saved sample: the E-ink frame differs per valid time, has the exact 3813-byte length, and its measured density per JMA colour class is monotonic in intensity (the experiment's disc measurement, automated).
- The LCD frames for the saved sample remain byte-identical to the current implementation.
- The existing server library suite passes; `render_eink_preview` tests are migrated to the new path.
- A rain-heavy real generation (live fetch on a rainy day, or a newly saved fixture) is rendered and inspected on the host before any device claim.
- Physical panel readability (coastline, rain extent, text) is confirmed by the user on a real E-ink device; host images alone do not close effectiveness (U-10).
