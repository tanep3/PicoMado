# CI-WEBP-20261105: WebP development library in server tests

GitHub Actions run 41987665098 for `cfd754d` passed the Python and firmware steps, then failed in `cargo test --locked --all-features --manifest-path service/Cargo.toml`: the linker could not find `-lwebp`. The server intentionally links to system libwebp for caricature originals (`service/src/caricature/originals.rs`). The runner lacked the development library; this is a CI host dependency, not a failing test assertion or the firmware flash gate.

The newest published run at investigation time, 42014983683 for `2de798d`, failed at the same server step with the same `rust-lld: error: unable to find library -lwebp` message.

Install Ubuntu's `libwebp-dev` before the existing server test command. Keep all test commands and the WebP encoder unchanged. Verify the workflow diff, local availability of `libwebp`, and the same Cargo test command. The remote run will only be confirmed after a separately authorized push.

Local verification: both Python commands and both firmware test scripts passed. The Cargo command linked and passed with local `libwebp` available: 334 library tests passed, one ignored; two server-binary tests and four JMA integration tests passed, with the live HTTPS test ignored. The first sandboxed Cargo run had 16 local-socket tests rejected by sandbox `EPERM`; the same command in an authorized socket-capable test environment passed. No device or service was touched.

After publishing this dependency fix, run 42018669679 passed the install step and reached the server tests. Two offline YouTube tests then failed because the clean runner did not have `ffmpeg` (`No such file or directory` at `service/src/youtube/tests.rs:396,642`). These tests synthesize local MP4 fixtures; they should continue to run. Extend the CI dependency step with Ubuntu's `ffmpeg` package, which supplies both `ffmpeg` and `ffprobe`. Local full Cargo tests already passed with these tools available.

Ubuntu 24.04 supplies FFmpeg 6.1, whose `scale` filter does not recognize `reset_sar=1` (`Option not found` in a local probe). The existing converter uses that option, so installing the package alone would leave the two tests failing. Convert source sample aspect ratio to square pixels with `scale=iw*sar:ih,setsar=1` before fitting into the existing 160×80 box. This preserves display aspect ratio on both FFmpeg 6.1 and 9 without relying on the newer option. Compare an anamorphic test frame's fitted dimensions across both versions, and rerun the affected tests with Ubuntu's `/usr/bin/ffmpeg` first on PATH.

Verification after the filter change: both affected YouTube tests passed with `/usr/bin/ffmpeg` 6.1, and the full Cargo suite passed with that PATH (334 library tests passed, one ignored; binary and JMA integration tests passed). The short conversion test also passed with the local FFmpeg 9. An anamorphic SAR 2:1 probe produced a 160×60 square-pixel fitted image on both versions, matching the previous FFmpeg 9 result.

Run 42020542109 remained in the dependency-install step for over 11 minutes. GitHub did not expose its live job log (the log endpoint returned 404), so the exact apt wait is unknown. Bound `apt-get update` to 180 seconds and the install to 300 seconds, use noninteractive apt with no recommended packages, and set a nine-minute step limit. These preserve the required libraries while making an apt/mirror stall fail visibly instead of waiting without a bound.
