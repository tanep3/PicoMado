# D-02 の要件照合とレビュー是正

`90ea981` のApp所有権貸出案は受入済みではない。mutexをIO中に保持しなくても、Appを一つの処理へ貸し出したまま後続の変更を待たせれば、表示切替の直列待ちは残る。退避した試作 `78237bc5a6293ecc76db8ba06883965a9590281f` は採用しない。

## 元の要件と保存の粒度

正本は[共通カーネルの状態管理](requirements/kernel.md#プラグイン-web-画面と責務境界)、[設計第3節](system-design-draft.md#3-状態の正本と保存境界)、AC-03・AC-13・AC-16。全状態のJSONを毎入力でSQLiteへ保存する実装は、これらの要件そのものではない。

| 状態 | 要求される保存・公開境界 |
| --- | --- |
| 登録/incarnation、利用ON/OFF、共通順序、端末・plugin設定、削除と関連outboxの無効化 | 改訂を検証し、保存成功後に確定として公開する。関連する変更は一つのtransactionにする。 |
| 前回選択plugin | 再起動後にも保持する永続対象。単に一時的な入力として保存対象から外さない。 |
| SUBのmode、browse/pin/cursor、オンライン判定、接続handle、frame送受信/描画の進行 | 再起動で復元しない一時状態。これらだけの変化に全世界の永続化は不要。旧session/display/incarnationの照合は引き続き必要。 |
| 取得セット、最後の正常取得時刻、完成素材 | plugin所有。大きな素材は共有lockの外で完成・検証し、短い索引切替と改訂照合で公開する。画像本体を毎入力のDB保存に混ぜない。 |

原要件は、選択の受信通知・表示開始とfsyncの厳密な先後までは定めていない。一方、現在の実装・追加契約は保存成功後に選択を公開する。これを黙って非同期保存へ変更しない。以下の修正はこの強い保存保証を維持する方針とする。

一時的なACK・browse・送信進行と、保存を要する設定・選択を別の遷移として扱う。一時遷移をSQLite待ちの所有権queueへ並べない。永続命令は最小限の不変deltaと期待改訂を保存workerへ渡し、完了を結果イベントとして戻す。公開時には現在の一時状態へ再検証して適用し、保存準備時のApp全体を置き換えない。描画frameの世代、browse/pin、同時に進んだACKを巻き戻さない。設定・削除による旧世代失効を優先する。

一つのSQLite databaseは同時に複数のwrite transactionを確定できない。そのwriter自体が停止中なら、保存成功を待つ新選択の公開も待つ。これはmutexの除去だけでは解決しない。重い素材の準備・serializeを短いcore transactionから除き、保存が不要な遷移を進めることが、現在の保存保証を維持した改善範囲である。「SQLite writer停止中でも新選択を必ず即表示する」まで要求するなら、表示後・保存前の異常終了時に最後の選択が失われ得る方式への変更、または独立したdurable journalの追加という別の設計選択になる。本修正でその変更を承認済みとは扱わない。

## 一つの呼出しに複数commitがある場合

現行`button`は、選択遷移を保存した後、別の遷移でframe要求を保存する。呼出し全体の`Result`と、各commitの成否は同じではない。1回目のcommit成功後に2回目が失敗・panicしても、1回目を未保存だったように扱わない。

1. 最後に成功したcommitまでの状態を、durable状態と公開snapshotの共通の境界とする。
2. 失敗したcommitのframe/effect・plugin変更・通知を公開しない。成功したprefixの通知は消さない。
3. panic時には未確定のmutable所有者を後続へ返さない。読み取り側を提供し続ける場合は、成功済みprefixのsnapshotを返す。prefixも更新不能なら明示的にunavailableとし、旧snapshotを現在の正本として提供し続けない。
4. 再起動時も保存成功prefixへ復帰し、後半の失敗したframe要求を復活させない。選択済みの通常画面を再要求する経路は既存の再接続規則に従う。

まず実SQLiteのtriggerで2回目の保存だけを失敗させる試験と、1回目の保存後に2回目の遷移をpanicさせる試験を追加する。DB本文、現在のview、outbox、通知、再起動時の選択を照合する。この試験の成功だけではD-02の非阻害を確認したことにはならない。

親は既存の保存成功後の選択公開を維持し、保存不要経路を分離する方針を確定した。追加の仕様判断は不要。具体的なsnapshot・一時入力・view合流の契約は[保存中の操作設計](application-live-state-design.md)を参照する。
